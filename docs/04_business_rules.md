# 04. 비즈니스 규칙

> 기준 문서: [01 MVP 범위](01_mvp_scope.md), [02 용어 정의](02_glossary.md), [03 DB 설계](03_db_design.md), [99 결정 기록](99_decisions.md)
>
> 03이 "무엇을 저장하는가"라면, 04는 **"언제, 어떤 조건에서 저장·변경할 수 있는가"**다.
> 여기 적힌 규칙은 서버 코드와 테스트의 기준이 되고, 규칙 ID는 05 API 설계의 오류 코드로 그대로 쓰인다.

> ⚠️ 표시는 실무 규칙을 단순화한 부분이다. 실무 확인 후 바뀔 수 있다.

## 1. 규칙을 지키는 세 겹의 방어선

| 방어선 | 역할 | 예시 |
|---|---|---|
| ① 화면 | 사용자가 실수하기 전에 안내 | 잔액 초과 금액을 입력하면 빨간 안내문 표시, 버튼 비활성화 |
| ② 서버 | **규칙의 실제 판정자.** 여러 테이블을 확인하고 트랜잭션으로 저장 | 잔액 계산 → 초과면 거부 → 통과하면 투자 + 이벤트 함께 저장 |
| ③ DB | 서버에 버그가 있어도 막는 최후 방어선 | 금액 음수 금지, 상태값 제한, 원장 수정 금지 (03 5장) |

화면에서 막았더라도 서버는 **항상 다시 검사**한다. 화면은 우회할 수 있기 때문이다 (API 직접 호출 등).

### 공통 처리 규칙

- **BR-COM-01 트랜잭션**: 돈이나 상태가 바뀌는 작업은 관련된 모든 저장(업무 문서 + 원장 + 통지 + 연동 이벤트)을 **하나의 트랜잭션**으로 묶는다. 하나라도 실패하면 전부 취소된다.
- **BR-COM-02 동시 작업 잠금**: 조합의 돈이 바뀌는 작업(투자, 캐피탈콜, 관리보수, 분배)은 시작할 때 해당 조합 행을 잠근다 (`SELECT ... FOR UPDATE`).
  > **왜?** 두 사람이 동시에 잔액 10억 조합에 각각 7억 투자를 누르면, 둘 다 "잔액 10억"을 보고 통과해 14억이 나갈 수 있다.
  > 잠금을 걸면 두 번째 요청은 첫 번째가 끝날 때까지 기다렸다가 줄어든 잔액(3억)으로 다시 검사받는다.
- **BR-COM-03 확정 후 잠금**: `issued`, `confirmed`, `published`, `sent`, `passed` 처럼 **외부에 알려졌거나 확정된 문서는 수정할 수 없다.** 바꿔야 하면 취소·정정 문서를 새로 만든다.
- **BR-COM-04 작성자 기록**: 사람이 만든 모든 데이터에 `created_by` 를 남긴다.

## 2. 조합 상태 이동

### 2-1. 상태 이동 조건

```
planning ──① → fundraising ──② → formed ──③ → operating ──④ → dissolved ──⑤ → liquidated
```

| 이동 | 규칙 ID | 조건 (모두 만족해야 함) | 이동할 때 함께 일어나는 일 |
|---|---|---|---|
| ① 기획 → 모집 | BR-FUND-01 | 규약 버전 1의 필수 조건이 모두 입력됨 | 이벤트 `fund.status_changed` |
| ② 모집 → 결성 | BR-FUND-02 | 조합원 명부 확정됨 (3-2) · **대표펀드매니저 지정됨** (BR-MGR-03) · **약정 총액 ≥ 최소 결성액** (D29) · 결성총회의 결성 안건 **가결** · 최초 캐피탈콜 발송됨 ⚠️ | `formation_date` = 결성총회일, 규약 버전 1 잠금, 이벤트 |
| ③ 결성 → 운용 | BR-FUND-03 | 등록 완료일 입력됨 ⚠️ | 이벤트 |
| ④ 운용 → 해산 | BR-FUND-04 | 해산총회의 해산 안건 **가결** | `dissolution_date` = 해산총회일, 이벤트 |
| ⑤ 해산 → 청산 | BR-FUND-05 | 보유 기업 전부 회수(남은 원금 0) · 최종 분배 `paid` · 현금 잔액 0 · 미마감 캐피탈콜 없음 | `liquidation_date`, 이벤트 |

- **BR-FUND-02·03 구현 세부** (R2-4): 결성 조건의 최소 결성액은 원장의 약정 합계로 검사한다. 최소 결성액 기준이 없는 조합 유형(신기술사업투자조합)은 검사하지 않고 체크리스트에 그 사실을 표시한다. 결성하면 결성일 = 결성 안건이 가결된 결성총회일, 규약 버전 1 적용일도 결성일로 바꾼다. 등록 정보는 결성 완료 상태에서만 입력·수정하며 (신청일 ≥ 결성일, 완료일 ≥ 신청일, 완료일 ≤ 오늘), 운용을 시작하면 잠긴다.
- **BR-INST-01 관계 기관**: 수탁은행·사무관리사·회계감사인은 조합당 종류별 1곳 (`DUPLICATE_INSTITUTION`). 청산 전까지 등록·수정·삭제할 수 있다.
- **BR-FUND-06 역방향 금지**: 상태는 앞으로만 이동한다. 잘못 이동했다면 되돌리는 대신 관리자 정정 기능(고도화)으로 처리한다.
- **BR-FUND-04·05 구현 세부** (R6): 해산일 = 해산 안건이 가결된 해산총회일. 청산 조건은 ① 보유 기업 남은 원금 0 ② 최종 분배 `paid` ③ 현금 잔액 0 ④ 초안·발송 상태의 캐피탈콜 없음(발송한 요청은 마감). 청산일 = 최종 분배일. 운용 중인 조합의 요약 화면에는 해산 안건이 가결됐거나 만기일이 지났을 때만 해산 조건표를 보여준다.
- **BR-FUND-07 존속 기간 경과 경고**: 만기일이 지났는데 `operating` 이면 대시보드에 경고를 표시한다 (차단은 하지 않음. 실무에서는 총회로 기간을 연장하기도 한다 ⚠️).

## 3. 모집·결성

### 3-00. 구성원 (D31)

- **BR-STF-01 사번 중복 금지**: 사번은 구성원마다 달라야 한다 (`DUPLICATE_EMPLOYEE_NO`).
- **BR-STF-02 퇴사 처리**: 퇴사일은 입사일 이후. **현재 담당 중인 조합이 있으면 퇴사 처리할 수 없다** (`STAFF_HAS_ACTIVE_FUNDS`) — 먼저 운용 인력을 교체해야 한다. 퇴사하면 로그인 계정이 자동으로 중지되고 기존 로그인도 끊긴다. 행은 지우지 않는다.
- **BR-STF-03 로그인 계정**: 구성원 1명당 계정 1개. 업무 이메일이 로그인 ID가 되며, 이메일이 없으면 계정을 만들 수 없다 (`EMAIL_REQUIRED`). 임시 비밀번호는 **만들 때 한 번만** 보여주고 DB에는 복원할 수 없는 형태로만 저장한다. 재발급하면 기존 로그인은 모두 끊긴다.
- **BR-STF-04 계정 중지**: 중지된 계정은 로그인할 수 없고, 이미 로그인한 세션도 즉시 무효가 된다 (`ACCOUNT_DISABLED`). 퇴사한 구성원의 계정은 다시 사용할 수 없다.
- **BR-STF-05 자기 자신 보호**: 자기 자신의 계정은 중지하거나 퇴사 처리할 수 없다 (`CANNOT_DISABLE_SELF`). 모든 관리자가 스스로를 잠가 시스템에 아무도 못 들어가는 상황을 막는다.
- 구성원 이름을 바꾸면 연결된 로그인 계정의 표시 이름도 함께 바뀐다.

### 3-01. 조합 운용 인력 (D32, R1-4에서 구현)

- **BR-MGR-01 대상**: 재직 중인 구성원만 운용 인력으로 지정할 수 있다.
- **BR-MGR-02 역할**: 대표펀드매니저(`lead`)는 조합당 동시에 1명. 한 구성원은 한 조합에서 동시에 한 역할만 맡는다 (DB가 직접 막음).
- **BR-MGR-03 결성 조건** ⚠️: 결성하려면 대표펀드매니저가 지정되어 있어야 한다 (BR-FUND-02). 핵심운용인력 최소 인원 등 추가 요건은 실무 확인 후 반영한다.
- **BR-MGR-04 결성 후 교체**: 기획·모집 중에는 자유롭게 지정·교체할 수 있다. **결성 이후에는 가결된 운용 인력 교체 안건(`manager_change`)이 있어야** 선임·해임할 수 있다 (`AGENDA_NOT_PASSED`).
- **BR-MGR-05 이력**: 교체는 기존 행에 해임일을 넣고 새 행을 추가한다. 이전 담당 이력은 지우지 않는다.
- **BR-MGR-06 날짜**: 선임일은 입사일 이후, 해임일·교체일은 기존 선임일 이후여야 한다 (`INVALID_DATE`). 교체하면 기존 담당의 해임일 = 새 담당의 선임일이다. 같은 사람의 역할을 바꾸는 것도 교체로 처리한다.

### 3-0. 출자자 기준 정보

- **BR-LP-01 사업자등록번호 중복 금지**: 같은 사업자등록번호의 출자자는 한 명만 등록할 수 있다 (`DUPLICATE_REGISTRATION_NO`). 하이픈 유무와 상관없이 숫자 10자리로 비교하고 `123-45-67890` 형태로 저장한다. 중복이면 기존 출자자를 함께 알려준다.
- **BR-LP-02 개인 식별번호 저장 금지**: 개인 출자자는 사업자등록번호를 입력하지 않으며, 주민등록번호 등 개인 식별번호는 어떤 형태로도 저장하지 않는다.
- **BR-LP-03 검색**: 이름·사업자등록번호·담당자명으로 검색한다. 검색어의 `%` `_` 는 글자 그대로 찾는다.

### 3-1. 출자 제안

- **BR-PROP-01 단계 이동**: `proposed → reviewing → committed` 또는 `→ declined`. `committed`, `declined` 는 되돌릴 수 없다.
  (재협상이 필요하면 거절 후 재제안이 아니라, 결성 전까지는 `committed` 의 확약 금액만 수정 가능)
- **BR-PROP-02 확약 금액**: `committed` 로 바꿀 때 `loc_amount > 0` 이 필수다.
- **BR-PROP-03 발송**: 제안을 발송하면 `proposal` 통지가 해당 LP 한 곳을 수신자로 만들어진다. 조합 상태가 `fundraising` 일 때만 가능하다.
- **BR-PROP-04 모집 달성률**: `committed` 제안의 확약 금액 합 ÷ 목표 결성액. 100%를 넘어도 막지 않는다 (초과 결성 가능).
- **BR-PROP-05 제안 1건**: 한 조합에서 한 출자자에게는 제안 1건만 만든다 (`DUPLICATE_PROPOSAL`, 기존 제안을 함께 알려준다). 제안 작성·수정·단계 이동은 기획·모집 중에만 할 수 있다.
- **BR-PROP-06 단계 이동 세부** (R1-5 구현):
  - 검토 중을 거치지 않고 `proposed → committed / declined` 로 바로 갈 수 있다 (오프라인으로 바로 회신받는 경우).
  - 확약·거절할 때 결정일(`decided_date`)을 남긴다. 기본값은 오늘, 제안일 이후여야 한다 (`INVALID_DATE`).
  - 확약 금액(`loc_amount`)은 확약 상태에서만 입력·수정한다. 비울 수 없다 (`LOC_AMOUNT_REQUIRED`).
  - 거절된 제안은 수정할 수 없다 (`PROPOSAL_CLOSED`).
- **BR-PROP-07 발송 세부**: `proposed`, `reviewing` 인 제안만 발송할 수 있다 (`PROPOSAL_CLOSED`). 제안서를 고쳐 다시 보낼 수 있도록 **재발송을 허용**하며, 매번 새 통지를 만든다 (BR-NTC-01). 통지 본문에는 조합 조건과 제안 금액만 넣고 내부 메모는 넣지 않는다. 발송과 같은 트랜잭션에서 `notice.sent` 이벤트를 해당 LP 대상으로 만든다.

### 3-2. 조합원 명부 확정

결성 전 마지막 준비 단계다. **확약(약속)을 약정(법적 금액)으로 바꾸는** 작업이다.

- **BR-MEM-01 대상**: `committed` 상태인 제안만 조합원이 될 수 있다. 확정할 때 LP별 최종 약정액을 입력하며, 기본값은 확약 금액이다.
- **BR-MEM-02 GP 출자 필수**: GP 조합원과 GP 약정액을 반드시 포함한다.
- **BR-MEM-03 GP 의무 출자 비율**: GP 약정액 ÷ 약정 총액 ≥ `gp_commitment_min_ratio`. 미달이면 확정 불가 (`GP_COMMITMENT_BELOW_MIN`).
- **BR-MEM-04 확정 시 함께 저장**: 조합원(`fund_members`) 생성 + 조합원별 `commitment` 원장 행 (`source_type = 'formation'`) + 연동 이벤트
- **BR-MEM-05 확정 후 변경**: 결성총회 가결 전까지는 명부를 취소하고 다시 확정할 수 있다 (원장은 취소 행으로 처리). 결성 이후에는 변경 불가.
  - 취소에는 사유가 필요하다. 결성 안건이 가결됐거나 캐피탈콜이 하나라도 있으면(초안 포함) 취소할 수 없다 (`ROSTER_LOCKED`).
  - 명부가 확정된 동안에는 규약 버전 1을 바꿀 수 없다 (`ROSTER_CONFIRMED`). 1좌 금액·GP 의무 출자 비율 검사가 깨지지 않게 하기 위해서다.
  - 확약된 제안이라도 명부에서 뺄 수 있다 (확약 후 철회한 LP). LP 조합원은 1명 이상이어야 한다.
  - GP 조합원의 원장 행은 알릴 LP가 없어 연동 이벤트를 만들지 않는다.
- **BR-MEM-06 약정 증액** ⚠️: 결성 이후 약정 증액은 **가결된 규약 변경 안건**이 있을 때만 가능하고, `commitment` 원장 행을 추가한다 (`source_type = 'terms_amendment'`). 감액·신규 조합원 가입·지분 양도는 고도화 단계.
  - (R5-1 구현) 증액일은 총회일 ~ 오늘, 1좌 배수는 증액일에 적용되는 규약 기준, 증액 후에도 GP 의무 출자 비율을 지켜야 한다 (`GP_COMMITMENT_BELOW_MIN` → GP 약정도 함께 늘린다). 원장의 원인 문서는 근거 안건. 한 안건으로 여러 조합원을 증액할 수 있고, 같은 안건으로 규약 새 버전도 만들 수 있다. `Idempotency-Key` 필수.
- **BR-MEM-07 1좌 단위**: 조합원 약정액은 1좌 금액의 배수여야 한다 (`COMMITMENT_NOT_UNIT_MULTIPLE`). 명부 확정과 약정 증액 때 검사한다 (R2).

### 3-3. 규약 (버전 관리)

- **BR-TERM-01**: 규약 버전 1은 `planning`, `fundraising` 상태에서만 수정할 수 있다. 결성되면 잠긴다.
- **BR-TERM-02**: 새 버전은 `terms_amendment` 유형의 **가결된** 안건이 있어야 만들 수 있고, 안건 하나당 새 버전 하나다.
- **BR-TERM-03**: 새 버전의 적용일은 해당 총회일 이후여야 한다.
- **BR-TERM-04**: 어떤 날짜에 적용되는 규약 = 적용일이 그 날짜 이전인 버전 중 가장 최신 버전. 모든 계산(관리보수, 분배, 가결 기준)은 이 규칙으로 규약을 찾는다.
- **BR-TERM-05 1좌 금액**: 개인투자조합은 1좌 금액 100만 원 이상 (`INVALID_UNIT_AMOUNT`). 조합 유형을 바꿀 때도 다시 검사한다.
- **BR-TERM-06 구현 세부** (R5-1): 새 버전은 결성·운용 중에만 만든다. 적용일은 총회일 이후이면서 직전 버전의 적용일 이후여야 한다 (버전 순서와 적용일 순서를 일치시켜 BR-TERM-04 조회가 흔들리지 않게). 같은 안건으로 두 번째 버전은 `AGENDA_ALREADY_USED`. 새 버전을 만들면 `fund.terms_updated` 이벤트를 남긴다. 조합 개요는 오늘 적용 중인 버전을 보여주고, 적용일이 아직 오지 않은 버전이 있으면 함께 알린다. 총회 가결 기준(BR-VOTE-04)도 오늘 적용 중인 버전에서 복사한다.

### 3-4. 최소 결성 기준 (D29)

조합 유형과 결성 주체에 따라 최소 결성액이 다르다. 기준표는 코드 한 곳(`lib/rules/fund-minimums.ts`)에서 관리하고, 화면 안내와 서버 검사가 같은 표를 쓴다.

| 조합 유형 | 결성 주체 | 최소 결성액 | 1좌 금액 |
|---|---|---|---|
| 벤처투자조합 | 창업기획자 | 10억 원 | - |
| 벤처투자조합 | 벤처투자회사 · 신기사 · 기타 | 20억 원 | - |
| 개인투자조합 | 전체 | 1억 원 | 100만 원 이상 |
| 신기술사업투자조합 | 전체 | ⚠️ 확인 필요 (검사하지 않음) | - |

> 출처: 사용자 제공 기준 (2026-09-27). ⚠️ 법령 원문 확인 필요 ([98 실무 확인 목록](98_practice_check.md))

- **BR-FUND-09 목표 결성액**: 조합을 만들거나 수정할 때 목표 결성액 < 최소 결성액이면 저장을 막는다 (`BELOW_MIN_FUND_SIZE`). 처음부터 결성할 수 없는 조합이기 때문이다.
- **BR-FUND-10 오타 경고**: 목표 결성액이 1조 원을 넘으면 화면에서 확인을 요청한다. 저장은 막지 않는다.
- 결성 시점에는 목표가 아니라 **실제 약정 총액**으로 다시 검사한다 (BR-FUND-02). 법적 요건은 이쪽이다.

## 4. 출자 요청 (캐피탈콜)

### 4-1. 요청 생성

- **BR-CALL-01 요청 가능 상태**: `formed`, `operating`. 단 `fundraising` 에서는 명부 확정 후 **최초 납입(`is_initial = true`)** 만 가능하다 ⚠️.
- **BR-CALL-02 요청 한도**: 전체 요청액 ≤ 조합의 잔여 약정액 합계 (`CALL_EXCEEDS_UNFUNDED`)
- **BR-CALL-03 조합원별 배분**: 조합원 요청액 = 전체 요청액 × 지분율에서 **원 미만 버림**
- **BR-CALL-04 1원 단위 나머지**: 버림으로 생긴 나머지(전체 요청액 − 조합원별 합계)는 **약정액이 가장 큰 조합원**에게 더한다. 약정액이 같으면 먼저 가입한 조합원에게 더한다. (D13 제안)
  ```
  예) 전체 요청 1억, 조합원 3명 지분율 각 1/3
      33,333,333 × 3 = 99,999,999 → 나머지 1원
      → 약정액이 가장 큰 조합원(동률이면 먼저 가입)에게 +1원 → 33,333,334
  ```
- **BR-CALL-05 조합원별 한도**: 조합원 요청액 ≤ 그 조합원의 잔여 약정액. 나머지 배분 때문에 1원이 넘치는 경우를 막기 위해,
  **"잔여 약정 전액 요청"** 옵션을 선택하면 비율 계산 대신 조합원별 잔여 약정액을 그대로 요청한다 (마지막 캐피탈콜용).
- **BR-CALL-06 날짜**: 납입 기한 ≥ 요청일

### 4-2. 발송과 납입

- **BR-CALL-07 발송**: `draft → issued`. 발송하면 요청이 잠기고(BR-COM-03), `capital_call` 통지가 LP 조합원 전원을 수신자로 만들어진다. GP 조합원에게는 통지를 만들지 않는다.
- **BR-CALL-08 납입 기록**: 조합원별 요청 항목에 대해 `contribution` 원장 행을 추가한다 (`source_type = 'capital_call_item'`). 여러 번 나눠 납입할 수 있다.
- **BR-CALL-09 초과 납입 금지**: 항목별 누적 납입액 ≤ 요청액 (`PAYMENT_EXCEEDS_CALL`)
- **BR-CALL-10 납입일**: 납입일 ≥ 요청일. 미래 날짜는 입력할 수 없다.
- **BR-CALL-11 납입 상태 판정** (뷰에서 계산)
  - 납입액 = 요청액 → `paid`
  - 0 < 납입액 < 요청액 → `partial`
  - 납입액 = 0, 오늘 ≤ 기한 → `pending`
  - 납입액 < 요청액, 오늘 > 기한 → `overdue`
- **BR-CALL-13 구현 세부** (R2-3): 최초 납입 여부(`is_initial`)는 입력받지 않고 조합 상태로 정한다 (모집 중 = 최초 납입). 결성 전에는 초안 포함 1건만 만들 수 있다. 배분은 반올림된 지분율이 아니라 약정액 비율로 원 단위까지 정확히 계산한다. 나머지 1원의 동률 기준은 가입일 → 같은 명부로 함께 가입했으면 GP → ID 순. 발송 때 잔여 약정을 다시 확인한다 (그 사이 다른 요청이 발송됐을 수 있음). 통지는 LP마다 따로 만들어 자기 요청액만 보이게 한다.
- **BR-CALL-12 마감**: `issued → closed`. 모든 항목이 `paid` 이면 자동 마감한다. 미납이 남아도 GP가 수동으로 마감할 수 있으며, 마감 후에도 미납 조합원의 납입은 기록할 수 있다.
- **BR-CALL-13 미납 조합원 제재** ⚠️: 연체이자, 지분 몰수 등은 규약마다 달라 MVP에서는 **미납 표시와 대시보드 경고만** 한다.

## 5. 딜 파이프라인과 투자

### 5-1. 딜 단계

```
sourcing → reviewing → ic → approved
    │          │   ↑    │
    └──────────┴───┴────┴──→ dropped
               (ic → reviewing: 투심위 보완 요청)
```

- **BR-DEAL-01 허용 이동**: 위 화살표만 허용한다. 단계를 건너뛸 수 없다 (발굴 → 투심위 불가).
- **BR-DEAL-02 종료 상태**: `approved`, `dropped` 는 종료 상태다. 드롭된 기업을 다시 검토하려면 **새 딜을 만든다** (D18 제안). 같은 기업의 과거 딜 이력이 함께 보인다.
- **BR-DEAL-03 드롭 사유 필수**: `dropped` 로 바꿀 때 `drop_reason` 필수
- **BR-DEAL-04 투자 확정 조건**: `approved` 로 바꿀 때 투자 예정 조합과 예상 금액이 필수다.
- **BR-DEAL-05 이력 기록**: 단계가 바뀔 때마다 `deal_stage_history` 에 한 행을 추가한다.
- **BR-DEAL-07 투심위 상정 조건** (2026-09-28 추가): 검토 → 투심위로 옮기려면 **딜 메모 1건 이상**과 **예상 투자 금액**이 있어야 한다 (`IC_REQUIREMENTS`). 금액은 이동 요청에서 함께 정할 수 있다. 투심위 → 검토 → 투심위로 다시 올릴 때도 같은 조건을 검사한다. 딜 보드에서는 메모가 없으면 알림 창으로 안내하고, 금액만 없으면 입력 창을 띄운다.
- **BR-DEAL-06 구현 세부** (R4-1):
  - 투자 예정 조합은 기획·모집·결성·운용 상태의 조합만 고를 수 있다. 투자 확정 때 조합·금액을 함께 넣을 수 있다 (`APPROVAL_REQUIREMENTS`).
  - 종료된 딜(투자 확정·드롭)은 정보를 고치거나 단계를 옮길 수 없다 (`DEAL_CLOSED`). 메모는 사후에도 남길 수 있다. 메모에는 작성 시점의 단계가 함께 기록된다.
  - 담당자는 사용 중인 로그인 계정 중에서 고른다 (`deals.owner_id → users`).
  - 기업 사업자등록번호는 출자자와 같은 형식으로 저장하고 중복 등록을 막는다 (`DUPLICATE_REGISTRATION_NO`).

### 5-2. 투자 집행

- **BR-INV-01 신규 투자 조건**: 조합 `operating` + 투자일이 **투자 기간 안** (결성일 ~ 결성일 + 투자 기간) + `approved` 딜 필수 + 한 딜에서 신규 투자는 1건만
- **BR-INV-02 후속 투자 조건**: 조합 `operating` + 같은 조합이 이미 투자한 기업 + 남은 원금이 0보다 큰 기업(전액 회수되지 않은 기업). 투자 기간이 지나도 허용한다 ⚠️.
- **BR-INV-03 투자 가능 잔액**: 투자 금액 ≤ 약정 총액 − 누적 투자액 − 누적 관리보수 (`EXCEEDS_INVESTABLE_AMOUNT`)
- **BR-INV-04 현금 잔액**: 투자 금액 ≤ 현금 잔액 (`INSUFFICIENT_CASH`, 안내: "캐피탈콜로 먼저 자금을 확보하세요") (D14 제안)
  > **왜 두 가지를 다 검사하나?** 투자 가능 잔액은 "약속된 돈 중 아직 쓸 수 있는 몫"이고, 현금 잔액은 "지금 통장에 있는 돈"이다.
  > 약정은 충분해도 아직 LP에게 돈을 받지 않았으면 투자할 수 없다. 둘 중 하나만 보면 현금이 마이너스가 되는 기록이 생긴다.
- **BR-INV-05 날짜**: 투자일 ≥ 결성일, 미래 날짜 불가
- **BR-INV-06 주목적 비율 경고**: 투자 후 주목적 투자 비율을 다시 계산해, 아래 경우 대시보드에 경고한다 (차단하지 않음)
  - 🟡 주의: 투자 기간이 1년 이내로 남았는데 비율 < 의무 비율
  - 🔴 미달: 투자 기간이 끝났는데 비율 < 의무 비율
  - ⚠️ 주목적 비율의 분모(약정 총액 vs 투자 총액)와 산정 시점은 조합마다 다를 수 있음
- **BR-INV-07 구현 세부** (R4-2):
  - 신규 투자의 딜은 **이 조합을 투자 예정 조합으로 확정한 딜**이어야 한다 (`DEAL_NOT_APPROVED`). 같은 딜로 두 번째 신규 투자는 막는다 (`DEAL_ALREADY_INVESTED`) — 추가 투자는 후속 투자로 기록한다.
  - 투자 기간 = 결성일 ~ 투자 기간 종료일 전날 (관리보수와 같은 기준). 기간 밖 신규 투자는 `OUTSIDE_INVESTMENT_PERIOD`.
  - 후속 투자 대상은 남은 원금이 있는 보유 기업 (`NOT_A_HOLDING`).
  - 투자 기록은 수정·삭제하지 않는다 (정정 기능은 고도화). 돈이 움직이므로 `Idempotency-Key` 필수.
  - 주목적 비율 경고는 투자 집행 응답·투자 집행 탭·조합 개요에 함께 표시한다. 의무 비율은 오늘 적용되는 규약 버전 기준.
- **BR-VAL-04 구현 세부** (R4-3): 평가는 운용·해산 상태에서만 기록한다. 평가 기준일은 첫 투자일 ~ 오늘 (`INVALID_DATE`), 같은 기준일 중복은 `DUPLICATE_VALUATION`, 투자하지 않은 기업은 `NOT_A_HOLDING`, 전액 회수된 기업은 `VALUATION_NOT_ALLOWED`. 포트폴리오의 총 가치 배수 = (회수액 + 보유 평가액) ÷ 투자 원금.

### 5-3. 기업가치 평가

- **BR-VAL-01**: 해당 조합이 투자한 적이 있는 기업만 평가할 수 있다.
- **BR-VAL-02**: 평가 기준일 ≥ 해당 기업 첫 투자일. 같은 기준일에 중복 평가 불가 (03의 유일 제약).
- **BR-VAL-03**: 전액 회수된 기업은 평가하지 않는다. 대시보드는 **보유 중인 기업의 최신 평가액**만 합산한다. 평가 기록이 없는 기업은 남은 원금을 평가액으로 간주한다.

## 6. 관리보수 ⚠️

실무 규칙이 조합마다 달라 가장 단순화가 많이 들어간 영역이다. (D16 제안)

- **BR-FEE-01 청구 단위**: 분기 단위로 청구한다. 같은 조합의 청구 기간은 서로 겹칠 수 없다 (`FEE_PERIOD_OVERLAP`).
- **BR-FEE-02 기간 범위**: 결성일 ≤ 기간 시작, 기간 끝 ≤ 해산일(해산 전이면 만기일)
- **BR-FEE-03 산정 기준**
  - 투자 기간 중: 기준 금액 = **약정 총액**, 요율 = `management_fee_rate`
  - 투자 기간 후: 기준 금액 = **투자 잔액**(누적 투자액 − 회수된 원금), 요율 = `management_fee_rate_after`
  - 기준 금액은 **기간 시작일 시점** 값을 쓴다
- **BR-FEE-04 기간 분할**: 청구 기간이 투자 기간 종료일에 걸치면 두 행으로 나눠 저장한다 (기준이 다르기 때문).
- **BR-FEE-05 계산식**: `보수 = 기준 금액 × 요율 × 기간 일수 ÷ 365` 에서 원 미만 버림. 계산에 쓴 기준 금액, 요율, 기간을 모두 행에 저장한다 (03 설계 의도).
- **BR-FEE-06 현금 확인**: 보수 ≤ 현금 잔액 (`INSUFFICIENT_CASH`)
- **BR-FEE-07 규약 적용**: 요율은 기간 시작일에 적용되는 규약 버전에서 가져온다 (BR-TERM-04).
- **BR-FEE-08 구현 세부** (R3):
  - 청구는 `{ 연도, 분기 }` 로 받는다. 결성일이나 만기일(해산했으면 해산일)에 걸친 분기는 그 날짜로 자른다. 존속 기간은 만기일 전날까지로 본다.
  - 투자 기간 = 결성일 ~ 투자 기간 종료일 전날. 종료일이 분기 안에 있으면 두 행으로 나누고, 행마다 그 구간 시작일의 기준 금액·요율을 쓴다. 일수는 양 끝 포함.
  - 아직 시작하지 않은 분기는 청구할 수 없다 (`INVALID_PERIOD`). 청구일은 기간 시작일 ~ 오늘 (`INVALID_DATE`). 보수가 0원이면 청구하지 않는다 (`ZERO_FEE`).
  - 결성·운용·해산 상태에서 청구할 수 있다. 청구 기록은 수정·삭제하지 않는다 (정정 기능은 고도화).

## 7. 총회와 의결

- **BR-MTG-01 결성총회**: `fundraising` 상태에서 조합원 명부 확정 후에만 열 수 있다. 결성 안건(`formation`)이 반드시 포함된다.
- **BR-MTG-02 해산총회**: 해산 안건(`dissolution`)이 반드시 포함된다.
- **BR-VOTE-01 의결 참여자**: 총회일 기준 해당 조합의 조합원 전원(GP 포함) ⚠️ 이해관계 안건의 GP 의결권 제한 여부
- **BR-VOTE-02 의결권 스냅샷**: 투표를 기록할 때 그 시점의 지분율을 `voting_power_ratio` 로 저장한다 (D4, 원칙 4).
- **BR-VOTE-03 가결 기준**: 찬성 의결권 합 ≥ 안건의 `quorum_ratio` → `passed`, 아니면 `rejected`.
  **분모는 출석한 조합원이 아니라 전체 의결권**이다 (D17 제안). 기권과 미투표는 찬성으로 세지 않는다.
- **BR-VOTE-04 가결 기준 복사**: 안건을 만들 때 그 시점 규약의 `quorum_ratio` 를 안건에 복사한다. 나중에 규약이 바뀌어도 이미 만든 안건의 기준은 바뀌지 않는다.
- **BR-VOTE-05 결과 확정**: 총회를 `held` 로 바꿀 때 모든 안건의 결과를 판정해 잠근다. 이후 투표 수정 불가.
- **BR-VOTE-07 LP 직접 투표** (D40): LP 시스템이 LP 연동 API로 본인 찬반을 안건별로 한 번에 제출한다 (전부 기록되거나 전부 실패). 소집 후 개최 처리 전까지 다시 제출할 수 있고, GP가 먼저 입력한 값도 덮어쓴다. LP가 직접 한 투표(`channel = lp_system`)는 GP가 바꿀 수 없다 (`LP_VOTED_DIRECTLY`). 의결권 스냅샷(BR-VOTE-02)은 GP 입력과 같다. GP 입력은 서면 결의서처럼 시스템 밖에서 받은 의사를 옮겨 적는 용도로 남는다.
- **BR-VOTE-06 가결의 효과**

  | 안건 유형 | 가결되면 가능해지는 것 |
  |---|---|
  | `formation` | 조합 결성 (BR-FUND-02) |
  | `terms_amendment` | 규약 새 버전 추가 (BR-TERM-02), 약정 증액 (BR-MEM-06) |
  | `dissolution` | 조합 해산 (BR-FUND-04) |
  | `report_approval`, `other` | 상태 변화 없음, 기록만 |

- **BR-MTG-03 소집 통지**: 총회를 만들고 소집하면 `meeting` 통지가 LP 조합원 전원에게 만들어진다.
- **BR-MTG-04 진행 순서** (R2-2 구현): 생성 → 소집 통지 → 투표 입력 → 개최 처리.
  - 소집 통지를 보낸 뒤에는 일정·안건을 바꿀 수 없다 (`DOCUMENT_LOCKED`). 바꾸려면 총회를 취소하고 새로 연다.
  - 투표는 소집 후에만 입력한다 (`MEETING_NOT_CONVENED`). 개최 처리는 총회일 당일 이후에만 할 수 있다 (`INVALID_DATE`).
  - 결성총회는 한 번에 하나만 예정할 수 있다 (`MEETING_ALREADY_SCHEDULED`). 결성 안건이 부결되면 새 결성총회를 열 수 있고, 가결된 뒤에는 열 수 없다 (`FORMATION_ALREADY_PASSED`).
  - 결성 안건은 결성총회에서만, 해산 안건은 해산총회에서만 다룬다 (`AGENDA_NOT_ALLOWED`).
  - 결성총회가 예정된 동안에는 명부를 취소할 수 없다 (의결권이 명부 기준이므로).
  - 가결 판정의 분모(전체 의결권)는 개최 처리 시점 조합원 지분율의 합이다. 지분율 반올림 때문에 합이 정확히 1이 아닐 수 있어, 1 대신 실제 합을 쓴다 (만장일치 기준이 반올림으로 깨지지 않게).

## 8. 정기 보고

- **BR-RPT-01 작성**: 조합 상태 `formed`, `operating`, `dissolved` 에서 작성할 수 있다.
- **BR-RPT-02 초안**: `draft` 동안에는 숫자가 조회할 때마다 최신 데이터로 다시 계산된다.
- **BR-RPT-03 발행**: `published` 로 바꾸는 순간 보고 기간 종료일 기준 숫자를 `snapshot` 에 얼려 저장하고 잠근다. `report` 통지가 LP 조합원 전원에게 만들어진다.
- **BR-RPT-04 정정**: 발행된 보고서는 고칠 수 없다. 정정 보고서를 새로 발행한다.
- **BR-RPT-05 스냅샷 내용**: 약정 총액, 누적 납입, 누적 투자, 투자 잔액, 평가액 합계, 누적 회수, 누적 분배, 누적 관리보수, 주목적 투자 비율, 포트폴리오 기업별 요약(기업명, 투자액, 평가액, 상태)
- **BR-RPT-06 구현 세부** (R5-2):
  - 기간은 `{ 월간·분기·반기·연간, 연도, 순번 }` 으로 정한다. 결성일 이전에 끝나는 기간은 보고할 수 없다 (`INVALID_PERIOD`). 같은 기간 초안은 1개 (`REPORT_DRAFT_EXISTS`).
  - 모든 숫자는 **기간 종료일 기준**으로 계산한다: 원장·투자·회수는 그날까지의 기록, 평가는 그날 이전 최신 평가, 관리보수는 청구일 기준. 스냅샷에는 기간 중 변동(납입·투자·회수·분배·관리보수), 현금 잔액, TVPI(분배 + 평가액 + 현금) ÷ 납입도 함께 넣는다.
  - 기간이 끝나기 전에는 발행할 수 없다 (`REPORT_PERIOD_NOT_ENDED`) — 끝나지 않은 기간의 숫자를 고정하지 않기 위해서.
  - 발행하면 LP 조합원 전원에게 `report` 통지 1건(수신자 여러 명)과 LP별 `notice.sent` 이벤트를 만든다. 같은 기간을 다시 발행하면 제목에 [정정]을 붙인다. 초안은 삭제할 수 있고 발행본은 삭제·수정할 수 없다 (`DOCUMENT_LOCKED`).

## 9. 회수

- **BR-EXIT-01 회수 가능 상태**: `operating`, `dissolved`
- **BR-EXIT-02 원금 한도**: 이번 회수 원금 ≤ 해당 기업의 남은 원금 (누적 투자액 − 이전 회수 원금) (`EXIT_EXCEEDS_COST`)
- **BR-EXIT-03 원금 기본값** ⚠️: 전량 회수면 남은 원금 전액, 일부 회수면 GP가 직접 입력한다 (주식 수 비율 자동 계산은 고도화)
- **BR-EXIT-04 상각**: `write_off` 는 회수 금액 0이 필수다.
- **BR-EXIT-05 회수 배수**: `회수 금액 ÷ 원금` (원금이 0이면 계산하지 않음)
- **BR-EXIT-06 날짜**: 회수일 ≥ 해당 기업 첫 투자일, 미래 날짜 불가
- **BR-EXIT-07 기록** (R6): 회수는 추가만 한다 (정정은 BR-EXIT-08). 회수 금액은 현금으로 들어오고 처분 원가만큼 투자자산이 줄어든다. 같은 트랜잭션에서 투자자산 처분 분개를 만든다 (BR-ACC-02). `Idempotency-Key` 필수. 전량 회수된 기업은 평가·후속 투자 대상에서 빠진다.
- **BR-EXIT-08 취소** (D39): 회수는 수정하지 않고 취소한 뒤 다시 기록한다. 운용·해산 중인 조합에서만, 사유 필수, 두 번 취소할 수 없다 (`ALREADY_REVERSED`). 취소된 회수는 포트폴리오·현금·보고서 합계에서 빠지고 목록에는 취소로 남는다. 처분 분개는 역분개한다 (역분개일은 회수일, 결산된 기간이면 오늘). 회수 대금이 빠지면 회수일 이후 현금이 줄어들므로, 그 사이 어느 날이라도 현금이 음수가 되면 막는다 (`INSUFFICIENT_CASH`, BR-FIN-02).

## 10. 분배와 성과보수 (워터폴) ⚠️

### 10-1. 워터폴 계산 방식 (D15 제안)

실무의 워터폴은 조합마다 매우 다양하다. MVP는 아래처럼 단순화하고, 단순화한 사실을 화면에도 표시한다.

- **조합 전체 기준, 누적 계산**: 매 분배 때 "처음부터 지금까지 분배한 총액"을 기준으로 단계를 다시 계산하고, 이전 분배에서 이미 나간 몫을 뺀 만큼을 이번 분배로 한다.
- **기준수익은 단리**: 납입 건마다 `납입액 × 기준수익률 × (분배일 − 납입일) ÷ 365` 를 합산한다.
- **GP 캐치업 없음**: 성과보수는 3단계 초과수익에서만 떼어간다.

```
누적 분배 총액 (이전 분배 + 이번 분배)
│
├─ 1단계 원금 반환 ─── 누적 납입액까지 ──────── 조합원 전원, 지분율대로
│
├─ 2단계 기준수익 ─── 기준수익 금액까지 ─────── 조합원 전원, 지분율대로
│
└─ 3단계 초과수익 ─── 나머지 전부
      ├─ (1 − 성과보수율) → 조합원 전원, 지분율대로
      └─ 성과보수율 ────── GP (carried_interest)
```

```
예) 누적 납입 100억, 기준수익 10억, 성과보수율 20%, 누적 분배 총액 150억
    1단계 원금 반환  100억
    2단계 기준수익    10억
    3단계 초과수익    40억 → 조합원 32억(80%), GP 성과보수 8억(20%)
```

### 10-2. 분배 규칙

- **BR-DIST-01 분배 가능 상태**: `operating`, `dissolved`. 최종 분배(`is_final`)는 `dissolved` 에서만 가능하다.
- **BR-DIST-02 금액 한도**: 분배 가능 금액 ≤ 현금 잔액 (`INSUFFICIENT_CASH`)
- **BR-DIST-03 최종 분배**: 최종 분배의 금액은 현금 잔액과 **정확히 같아야** 한다 (청산 후 조합에 돈이 남으면 안 됨).
- **BR-DIST-04 계산 저장**: `draft` 에서 워터폴 계산 결과를 조합원 × 단계별로 `distribution_items` 에 저장한다. 조합원별 배분은 BR-CALL-03, 04와 같은 버림·나머지 규칙을 쓴다.
- **BR-DIST-05 확정**: `draft → confirmed`. 잠기고 `distribution` 통지가 LP 조합원 전원에게 만들어진다.
- **BR-DIST-06 지급**: `confirmed → paid`. 조합원별 합계를 `distribution` 원장 행으로 추가한다 (`source_type = 'distribution_item'`). GP의 성과보수도 GP 조합원 원장에 포함된다.
- **BR-DIST-08 진행 중 분배 1건** (R6): 초안·확정 상태의 분배는 조합당 하나만 둔다 (`DISTRIBUTION_IN_PROGRESS`). 누적 워터폴이 앞 분배의 결과를 기준으로 하기 때문이다. 최종 분배도 조합당 하나 (`FINAL_DISTRIBUTION_EXISTS`).
- **BR-DIST-09 조합원별 배분** ⚠️ (R6): 원금 반환은 조합원별 **누적 납입액** 비율, 기준수익은 조합원별 **기준수익**(각자 납입 건별 단리) 비율, 초과수익은 **약정 비율(지분율)**, 성과보수는 GP 조합원 전액. 원 미만 버림, 나머지는 약정액이 가장 큰 조합원 (BR-CALL-04와 같은 순서).
- **BR-DIST-10 확정 시 재계산** (R6): 확정할 때 워터폴을 다시 계산해 초안과 다르면(초안 이후 납입·취소 등) 확정하지 않는다 (`DISTRIBUTION_STALE`). 초안을 지우고 다시 만든다.
- **BR-DIST-11 지급일** (R6): 분배일(= 지급일)이 된 뒤에 지급 처리한다. 지급 시 분배일 기준 사용 가능 현금을 다시 검사한다 (BR-FIN-02). 분개는 분배 1건 = 1건: 원금 반환분은 `출자금반환`, 나머지(기준수익·초과수익·성과보수)는 `이익분배금` ⚠️ (성과보수를 비용이 아닌 이익 분배로 처리, 실무 확인 29).
- **BR-DIST-12 취소** (D39): 확정·지급한 분배를 `cancelled` 로 남긴다 (초안은 삭제). 누적 워터폴은 앞 분배 결과를 기준으로 하므로 **마지막 분배부터 거꾸로** 취소한다 (`LATER_DISTRIBUTION_EXISTS`). 지급했던 분배면 조합원 원장에 취소 행(음수, BR-LED-02)을 남기고 분배 분개를 역분개한다. 돈이 돌아오는 날이라 둘 다 **오늘 날짜**. LP 조합원에게 취소 통지를 보낸다. 취소된 분배는 워터폴 누적·성과보수 합계에서 빠지고, 최종 분배를 취소하면 다시 최종 분배를 만들 수 있다. 사유 필수, 운용·해산 중인 조합에서만.
- **BR-DIST-07 과다 분배** ⚠️: 누적 계산에서 이전 분배가 이미 앞 단계 몫을 넘은 경우(예: 이후 추가 납입으로 원금 반환 한도가 늘어남), 그 단계의 이번 분배는 0으로 처리한다. GP 성과보수 반환(클로백)은 고도화 단계.

## 11. 원장

- **BR-LED-01 추가만**: 원장 행은 수정·삭제할 수 없다 (D5). DB 권한과 트리거로도 막는다.
- **BR-LED-02 취소**: 취소 행은 원래 행과 조합원·구분·원인 문서가 같고, 금액은 정확히 반대다. 한 행은 한 번만 취소할 수 있다 (`ALREADY_REVERSED`).
- **BR-LED-03 원인 필수**: 모든 원장 행은 원인 문서(`source_type`, `source_id`)를 가진다. 원인 없이 돈을 기록할 수 없다.
- **BR-LED-05 취소 범위** (R3): 화면·API에서 직접 취소하는 것은 납입(`contribution`) 행뿐이다. 약정은 명부 취소(BR-MEM-05)로, 분배는 분배 문서(R6)로 정정한다 (`REVERSAL_NOT_ALLOWED`). 취소하면 현금이 줄어들므로, 이미 투자·관리보수로 쓴 납입금이라 현금 잔액이 음수가 되면 막는다 (`INSUFFICIENT_CASH`). 취소 사유(메모)는 필수이고, 취소 행도 `ledger.entry_created` 이벤트로 LP에게 알린다.
- **BR-LED-04 연동**: 원장 행이 추가될 때마다 `ledger.entry_created` 이벤트를 같은 트랜잭션으로 만든다 (대상 LP = 해당 조합원의 LP).

## 11-2. 조합 재무 (D34)

- **BR-EXP-01 기타 비용 기록**: 결성·운용·해산 상태에서 기록한다. 지급일은 오늘 이전, 금액은 현금 잔액 이하 (`INSUFFICIENT_CASH`). `Idempotency-Key` 필수.
- **BR-EXP-02 취소**: 지우지 않고 취소 시각·사유를 남긴다. 취소된 비용은 모든 합계에서 빠진다. 두 번 취소할 수 없다 (`ALREADY_REVERSED`).
- **BR-EXP-03 잔액 반영**: 투자 가능 잔액 = 약정 − 투자 − 관리보수 − **기타 비용**, 현금 잔액 = 납입 + 회수 − 투자 − 관리보수 − **기타 비용** − 분배. 정기 보고 스냅샷에도 누적·기간 중 기타 비용을 넣는다 (D34 이후 발행분부터).
- **BR-FIN-01 현금 흐름 장부**: 출자금 납입(취소 포함)·분배·투자·회수·관리보수·기타 비용을 날짜순으로 모아 누적 잔액과 함께 보여준다. 같은 날짜 안에서는 들어온 돈을 먼저 둔다. 따로 저장하지 않고 원본에서 계산한다 (D7). 걸러 볼 때도 잔액은 전체 기간 기준 실제 잔액이다.
- **BR-FIN-02 거래일 기준 현금**: 돈을 내보내는 기록(투자·관리보수·기타 비용·납입 취소)은 **거래일 기준 사용 가능 현금** 이하여야 한다 (`INSUFFICIENT_CASH`, 거래일과 한도를 함께 안내). 사용 가능 현금 = min(거래일 기준 잔액, 거래일 이후 모든 날짜별 마감 잔액). 과거 날짜로 출금을 넣어도 이후 어느 시점의 잔액도 음수가 되지 않게 하기 위해서다. (2026-09-28 추가. 이전에는 오늘 잔액만 검사해 샘플 데이터에 납입일보다 앞선 투자가 1건 있었고, 투자일을 납입일로 바로잡았다.)
- **BR-FIN-03 약식 재무제표**: 재무 탭은 업무 기록에서 바로 계산한 약식 재무상태표·손익계산서를 보여준다 (원가 기준).
  - 재무상태표: 자산(현금및현금성자산, 투자자산 취득원가) = 부채(아직 미기록, 0) + 자본(출자금 납입분 − 분배금 + 이익잉여금). 화면에서 대차 일치 여부를 함께 표시한다.
  - 손익계산서(누적): 영업수익 = 투자자산처분손익(처분대가 − 처분 원가), 영업비용 = 관리보수 + 기타 비용, 당기순이익 = 수익 − 비용. 미실현 평가손익(공정가치 − 장부가액)은 참고로만 보여주고, 공정가치 기준 순자산가치(NAV) = 자본총계 + 미실현 평가손익.
  - 출자 약정 중 미납입분은 재무상태표에 넣지 않고 주석으로 보여준다.
  - ⚠️ 한계: 비용은 지급 시점 인식(미지급 부채 없음), 분배금은 출자금 반환·이익 분배 미구분. 정식 재무제표는 회계 모듈(분개·계정별 원장·결산)에서 제공한다 (D34, 실무 확인 25~28).

## 11-3. 회계 (D35)

- **BR-ACC-01 복식부기**: 모든 분개는 차변 합 = 대변 합, 줄 2개 이상, 한 줄은 차변 또는 대변 하나 (`JOURNAL_NOT_BALANCED`). 서버가 검사하고, DB 트리거가 커밋 시점에 한 번 더 검사한다. 분개장은 추가만 가능하고 수정·삭제할 수 없다.
- **BR-ACC-02 자동 분개**: 업무 기록과 **같은 트랜잭션**에서 분개를 만든다. 업무 기록 하나에 자동 분개 하나 (역분개 제외, DB 유일 인덱스).

  | 업무 기록 | 차변 | 대변 |
  |---|---|---|
  | 출자금 납입 (캐피탈콜 납입) | 현금및현금성자산 | 출자금 |
  | 출자금 납입 취소 | 출자금 | 현금및현금성자산 |
  | 투자 집행 | 투자자산 | 현금및현금성자산 |
  | 투자자산 처분 (R6) | 현금(처분대가) · 처분손실 | 투자자산(처분 원가) · 처분이익 |
  | 관리보수 청구 | 관리보수 | 현금및현금성자산 |
  | 기타 비용 | 해당 비용 계정 (회계감사수수료·수탁보수 등) | 현금및현금성자산 |
  | 기타 비용 취소 | 원래 분개의 역분개 (지급일, 그 기간이 결산됐으면 오늘) | |
  | 분배금 지급 (R6, 분배 1건 = 분개 1건) | 출자금반환(원금 반환분) · 이익분배금(나머지) — 둘 다 자본 차감 | 현금및현금성자산 |

  약정(명부 확정·약정 증액)은 재무상태표에 넣지 않는 약정 사항이라 분개하지 않는다. 자동 분개는 수동으로 역분개할 수 없고, 원래 업무 화면에서 취소해야 한다 (`REVERSAL_NOT_ALLOWED`).
- **BR-ACC-03 결산**: 사업연도는 1/1~12/31, 결성한 해는 결성일부터 ⚠️ (실무 확인 25). 사업연도가 끝난 뒤, 이전 연도부터 차례로 결산한다 (`PREVIOUS_YEAR_OPEN`). 결산하면 수익·비용 계정 잔액을 이익잉여금으로 대체하는 결산 분개를 만들고 그 기간을 잠근다. 잠긴 기간 날짜로는 업무 기록·분개를 넣을 수 없다 (`PERIOD_CLOSED`). 잘못을 고치려면 결산을 재개한다 (BR-ACC-07).
- **BR-ACC-04 수동 분개**: 미지급비용 같은 발생주의 조정, 예금 이자처럼 업무 화면이 없는 거래를 기록한다. 분개일은 오늘 이전, 열린 기간. 현금 계정을 줄이면 거래일 기준 사용 가능 현금을 검사한다 (BR-FIN-02). 수동 분개는 역분개로만 정정한다 (역분개일은 오늘).
- **BR-ACC-05 재무제표**: 재무상태표(기준일) = 자산 / 부채 / 자본. 결산하지 않은 기간의 순이익은 자본의 "미처분 당기순이익"으로 보여준다. 손익계산서(기간)는 결산 대체 분개를 빼고 계산한다. 투자자산은 원가법 ⚠️ (실무 확인 27). 재무제표 화면에서 현금 계정 잔액과 업무 기록 기준 현금출납장 잔액이 같은지 대사한다.
- **BR-ACC-06 소급 분개**: 회계 모듈 도입 전 업무 기록은 같은 규칙으로 한 번 소급 분개한다 (`npm run db:backfill-journal`, 이미 분개된 기록은 건너뜀).
- **BR-ACC-07 결산 재개** (D39): 마지막으로 결산한 사업연도부터 거꾸로 연다 (`LATER_YEAR_CLOSED`). 결산 분개를 기말 날짜로 역분개하고 기간 잠금을 푼다. 결산 기록은 지우지 않고 재개 시각·사유를 남기며, 고친 뒤 다시 결산한다 (사업연도당 유효한 결산은 하나). 청산한 조합은 재개할 수 없다.

## 12. 통지와 LP 연동

### 12-1. 통지가 자동으로 만들어지는 경우

| 계기 | 통지 유형 | 수신자 |
|---|---|---|
| 출자 제안 발송 | `proposal` | 해당 LP 1곳 |
| 캐피탈콜 발송 | `capital_call` | LP 조합원 전원 (각자 자기 요청액 포함) |
| 총회 소집 | `meeting` | LP 조합원 전원 |
| 정기 보고 발행 | `report` | LP 조합원 전원 |
| 분배 확정 | `distribution` | LP 조합원 전원 (각자 자기 분배액 포함) |
| GP 수동 작성 | `general` | GP가 선택한 LP |

- **BR-NTC-01 발송 후 잠금**: 발송된 통지는 수정·삭제할 수 없다. 정정이 필요하면 새 통지를 보낸다.
- **BR-NTC-02 확인 기록**: LP 확인 시각은 LP 시스템이 연동 API로 알려줄 때만 기록된다. GP가 직접 입력할 수 없다.
- **BR-NTC-03 일반 공지** (R7): 모집·결성·운용·해산 상태에서 작성한다. 초안 → 발송 순서이고, 수신자를 비우면 LP 조합원 전원이다. 조합원이 아닌 LP에게는 보낼 수 없다 (`NOT_A_MEMBER`). 발송하면 수신 LP마다 `notice.sent` 이벤트를 만든다. 조합 탭 **총회·보고 > 통지**에서 자동 통지(출자 제안·캐피탈콜·총회·보고·분배)와 함께 LP별 확인 현황을 본다.

### 12-2. 연동 이벤트

- **BR-EVT-01 같은 트랜잭션**: LP 공개 등급(03 7장)이 🟢, 🔵 인 데이터가 바뀌면 이벤트를 같은 트랜잭션 안에서 만든다 (D12).
- **BR-EVT-02 이벤트 종류**

  | 이벤트 | 계기 |
  |---|---|
  | `fund.status_changed` | 조합 상태 이동 (결성 시 결성일 포함) |
  | `fund.updated` | 등록 정보·관계 기관 변경 (R2-4 추가) |
  | `fund.terms_updated` | 규약 새 버전 |
  | `member.joined` | 조합원 명부 확정 |
  | `ledger.entry_created` | 원장 행 추가 (약정·납입·분배·취소) |
  | `notice.sent` | 통지 발송 |
  | `meeting.result_finalized` | 총회 결과 확정 |

- **BR-EVT-03 재전송**: 전송 실패 시 `failed` 로 두고 재시도한다. 5회 연속 실패하면 재시도를 멈추고 대시보드에 표시한다.
- **BR-EVT-04 순서와 중복**: 같은 LP에게 가는 이벤트는 생성 순서대로 보낸다. 받는 쪽(LP 시스템)은 이벤트 ID로 중복을 거른다.
- **BR-EVT-05 🔴 비공개 데이터 차단**: 🔴 등급 테이블의 데이터는 이벤트 `payload` 에 절대 넣지 않는다.
- **BR-EVT-06 전송** (R7): 웹훅 주소(`LP_SYSTEM_WEBHOOK_URL`)가 설정되어 있을 때만 보낸다. 없으면 `pending` 으로 쌓이고, LP 시스템은 `GET /api/lp/v1/events?after=` 로 직접 가져갈 수 있다. 서명은 `HMAC-SHA256(LP_WEBHOOK_SECRET, 타임스탬프 + "." + 본문)`. 실패하면 1분·5분·30분·2시간·12시간 간격으로 다시 보내고 5번째 실패에서 `failed` 로 멈춘다. 같은 LP의 뒤 이벤트는 앞 이벤트가 전송될 때까지 기다린다 (BR-EVT-04). GP는 **LP 연동** 화면에서 지금 전송·재전송한다.
- **BR-EVT-07 자동 전송** (D41): Vercel Cron 이 `/api/cron/dispatch-events` 를 주기적으로 부른다 (`Authorization: Bearer {CRON_SECRET}`, 없거나 틀리면 거부). 무료(Hobby) 요금제라 **하루 1회**(오전 9시 KST) ⚠️ — 그 사이에는 GP가 지금 전송한다. 자동·수동 전송은 같은 잠금(`scheduled_jobs`, 5분 임대)을 써서 동시에 돌지 않는다. 먼저 잡은 쪽만 보내고 나머지는 건너뛴다. 마지막 실행(자동/수동·결과·오류)은 LP 연동 화면에 보인다.
- **BR-FILE-01 첨부** (D41): 규약 버전별 원문과 정기 보고서에 PDF를 첨부한다. PDF만(파일 앞부분 `%PDF-` 확인), 파일당 4MB까지 ⚠️ (서버를 거쳐 올리므로 Vercel 함수 요청 크기 안쪽). 파일은 비공개 Vercel Blob 에 두고, 열기는 로그인한 GP가 서버 경로로만 한다. 지우면 목록·LP에서 빠지고 기록과 파일은 남는다. 저장소가 연결되지 않았으면 올릴 수 없다 (`STORAGE_NOT_CONFIGURED`).
- **BR-FILE-02 LP 공개** (D41): LP 연동 API는 오늘 적용 중인 규약 버전의 원문과 **발행된** 보고서의 PDF만 목록에 넣고 내려받게 한다 (🔵). 초안 보고서·삭제한 파일은 404.

### 12-3. LP 연동 API (R7)

- **BR-LPAPI-01 인증**: `Authorization: Bearer {LP_SYSTEM_API_KEY}`. 키가 없거나 틀리면 `401`, 서버에 키가 설정되지 않았으면 `503 LP_API_DISABLED`.
- **BR-LPAPI-02 공개 등급**: 🟢 본인 것만, 🔵 조합원인 조합만(아니면 `403 FORBIDDEN`), 🟡 정기 보고 스냅샷으로만, 🔴 반환하지 않음. `memo`·`created_by`·내부 문서 ID(`source_id`)·LP 연락처는 어떤 응답에도 넣지 않는다. 원장 출처는 "제2차 캐피탈콜"처럼 LP가 이해할 수 있는 정보로 바꿔 준다.
- **BR-LPAPI-03 미리보기**: GP 출자자 화면의 **LP 공개 데이터 미리보기**는 LP 연동 API와 같은 함수로 그린다 (LP 시스템이 보는 것과 항상 같다).

## 12-2. 권한과 감사 로그 (D42)

- **BR-AUTH-01 역할**: 로그인 계정마다 역할 하나. `admin`(관리자) · `manager`(운용) · `finance`(재무) · `viewer`(조회). 새 계정은 운용.
  | 역할 | 할 수 있는 것 |
  |---|---|
  | 관리자 | 모든 작업 + 구성원·계정·권한, LP 연동, 감사 로그 |
  | 운용 | 딜·투자·조합 운영 기록 (출자 제안, 명부, 캐피탈콜 작성·발송, 투자·평가·회수, 분배 작성·확정, 총회, 보고, 공지, 규약) |
  | 재무 | 회계(분개·결산·재개), 기타 비용, 관리보수 청구, 납입 확인, 분배 지급, 납입 취소 |
  | 조회 | 모든 화면 조회만 |
  분배 취소·파일 첨부는 운용·재무 모두. 계산만 하는 미리보기는 모두.
- **BR-AUTH-02 검사 위치**: GP 내부 API의 모든 요청이 한곳(`withUser` → `lib/auth/permissions.ts`)에서 역할을 검사한다 (`403 FORBIDDEN`, 필요한 역할을 알려준다). 역할이 바뀌면 다음 요청부터 바로 적용된다. 메뉴는 역할에 맞게 숨기고(시스템 메뉴는 관리자만), 관리자 전용 화면은 권한 안내를 보여준다. 업무 화면의 버튼은 보일 수 있지만 서버가 막는다 ⚠️.
- **BR-AUTH-03 권한 변경**: 관리자만, 자기 자신의 권한은 바꿀 수 없다 (`CANNOT_CHANGE_OWN_ROLE`). 그래서 관리자가 0명이 되지 않는다.
- **BR-AUTH-04 감사 로그**: 모든 쓰기 요청(GP 사용자 · LP 시스템 · 주기 작업)과 로그인(실패 포함)·로그아웃을 남긴다. 권한이 없어 막힌 요청도 남긴다. 누가(이름·역할 스냅샷), 언제, 무엇을(주소 모양), 어느 조합, 결과(응답 코드·오류 코드), IP. 요청 본문은 저장하지 않는다 (비밀번호 등). 로그인 실패는 시도한 이메일만. 조회(GET)와 계산 미리보기는 남기지 않는다. 기록은 수정·삭제할 수 없다 (DB 트리거). 관리자가 **감사 로그** 화면에서 사용자·조합·기간·결과로 찾아본다.
- **BR-AUTH-05 배포 환경 데모** (D43, D44): 배포된 사이트는 데모 전용 DB(Neon `demo` 브랜치)를 쓰고, 이 DB는 **매일 03:00 KST에 원래 데모 데이터로 초기화**된다. 그래서 데모 버튼으로 들어오면 **관리자로 모든 기능을 써 볼 수 있다**. 데모 전용 DB 설정(`APP_DATABASE_URL`)이 없는 배포(예: Preview)에서는 데모 세션이 **조회 전용**이다 (세션 권한 상한 `role_cap = viewer`, 안내 띠 표시). 로컬 개발은 관리자 그대로.

## 14. 이 문서에서 내린 결정 (확정)

아래 결정은 2026-09-27 확정되어 [99 결정 기록](99_decisions.md)에 옮겼다.

- **D13. 1원 단위 나머지 처리**: 원 미만 버림 후 나머지는 **약정액이 가장 큰 조합원**에게 (동률이면 먼저 가입한 조합원).
  - 다른 선택지: 소수점 아래가 큰 순서로 1원씩 나눠주기(최대 잔여 방식, 더 공평하지만 설명이 복잡함) / 항상 GP가 부담
- **D14. 투자 시 현금 잔액도 검사**: 약정 기준 잔액뿐 아니라 현금이 부족해도 투자를 막는다. 캐피탈콜 → 투자 순서를 시스템이 강제한다.
- **D15. 워터폴 단순화**: 조합 전체 기준 누적 계산, 기준수익 단리, GP 캐치업 없음, 클로백 없음.
- **D16. 관리보수 단순화**: 분기 청구, 일할 계산(365일), 투자 기간 전후로 기준 금액 전환, 경계에 걸치면 기간 분할.
- **D17. 가결 기준**: 출석이 아니라 **전체 의결권 대비** 찬성 비율. 기권·미투표는 찬성이 아니다.
- **D18. 드롭된 딜은 종료**: 다시 검토하려면 새 딜을 만든다. 단계별 소요 기간 분석이 깨끗해진다.
- **D19. 최초 납입은 결성 전 허용**: 명부 확정 후 결성총회 전에 최초 캐피탈콜을 발송할 수 있고, 결성의 조건으로 둔다 ⚠️ 납입 완료까지 요구할지는 실무 확인.
