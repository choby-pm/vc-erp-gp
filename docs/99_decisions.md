# 99. 결정 기록

설계 중 내린 결정과 그 이유를 남긴다. 결정이 바뀌면 지우지 않고 새 번호로 추가한다.

---

## D1. MVP 범위: 조합 생애주기 6단계 전체 (2026-09-27 확정)

- **결정**: 기획 → 모집 → 결성 → 운용 → 보고·총회 → 회수·청산까지 모두 MVP에 포함한다.
- **조건**: 기능이 얇아지면 안 된다. 각 단계는 입력 → 처리 → 결과가 끝까지 이어져야 한다. 개발 기간이 늘어나는 것은 감수한다.
- **검토한 선택지**
  - 1~4단계 + 최소 보고: 빠르지만 조합 운영의 끝(분배·청산)을 경험할 수 없다
  - 결성까지만: 투자가 빠진 VC ERP가 된다
  - **6단계 전체 (채택)**: GP 업무 전체를 이해하고 있다는 것을 보여줄 수 있다
- **리스크와 대응**: 성과보수·관리보수·의결 기준은 실무 규칙이 틀리기 쉽다 → 단순화한 규칙으로 구현하고 문서에 ⚠️로 밝힌 뒤, 해당 릴리스 전에 실무 확인을 받는다.

## D2. LP 시스템 연동: DB 분리 + GP 원본 + API 연동 (2026-09-27 확정)

- **결정**: LP 시스템은 별도 앱·별도 DB로 만든다. GP DB가 원본이고, LP 시스템은 GP가 제공하는 연동 API와 이벤트 알림으로 GP 데이터를 받는다.
- **LP DB에 두는 것**: LP 계정, 통지 읽음 여부 등 LP 시스템에서만 생기는 데이터
- **검토한 선택지**
  - 같은 앱 안에 LP 화면: 가장 쉽지만 시스템 간 연동 경험을 보여줄 수 없다
  - DB 공유 + LP 전용 API: DB가 하나라 LP 시스템이 GP 구조에 묶인다
  - DB 완전 분리 + 전체 복제 동기화: 실제 대규모 서비스와 가깝지만 동기화 실패 처리가 과하게 어렵다
  - **DB 분리 + GP 원본 + API (채택)**: 복제를 최소화해 동기화 문제를 줄이면서, 시스템 간 연동 설계를 경험할 수 있다
- **비용**: Neon, Vercel 모두 무료 플랜 안에서 가능 (가입 시 한도 재확인)
- **GP 쪽에서 지금 준비할 것**: 모든 GP → LP 요청을 '통지'로 기록, 데이터별 LP 공개 여부 구분, LP 연동용 API

## D3. 금액은 원 단위 정수로 저장 (2026-09-27 확정)

- **결정**: 모든 금액은 `bigint`(정수), 원 단위로 저장한다. 비율은 `numeric`(정확한 소수)으로 저장한다.
- **이유**: 실수형(`float`)은 계산 과정에서 미세한 오차가 생긴다. 분배처럼 여러 조합원에게 나누는 계산에서 오차가 쌓이면 합계가 맞지 않는다.

## D4. 지분율은 약정액 기준 하나로 통일 (2026-09-27 확정)

- **결정**: 캐피탈콜 배분, 총회 의결권, 분배 비율 모두 `조합원 약정액 ÷ 약정 총액`을 쓴다.
- **검토한 선택지**: 분배를 납입액 기준으로 하는 방식도 실무에 있다. 미납 조합원이 있으면 두 기준의 결과가 달라진다.
- **이유**: MVP에서는 기준을 하나로 통일해 계산 흐름을 단순하게 유지한다. ⚠️ 실무 확인 후 필요하면 분배 기준을 규약 조건으로 추가한다.

## D5. 원장은 추가만 허용 (2026-09-27 확정)

- **결정**: 원장 행은 수정·삭제하지 않는다. 틀린 기록은 반대 금액의 취소 행을 추가한 뒤 올바른 행을 다시 추가한다.
- **이유**: 누가 언제 무엇을 바꿨는지 모두 남는다. 실제 회계 시스템과 같은 방식이고, LP 시스템에 변경 이력을 그대로 보여줄 수 있다.

## D6~D12. DB 설계 원칙 (2026-09-27 확정)

상세 근거는 [03 DB 설계](03_db_design.md) 각 테이블의 "설계 의도"에 있다.

- **D6. 기본 키는 UUID**: 두 시스템(GP·LP)이 ID를 그대로 공유할 수 있고, ID로 데이터 개수나 순서를 짐작할 수 없다. 사람이 읽기 어려운 단점은 화면에 회차 번호(`call_no` 등)를 따로 보여줘서 보완한다.
- **D7. 합계·잔액은 저장하지 않고 뷰로 계산**: 원본이 하나라 숫자가 어긋날 수 없다. 데이터가 매우 많아져 느려지면 그때 캐시를 추가한다.
- **D8. 캐피탈콜 요청은 원장에 넣지 않음**: 원장에는 확정된 돈(약정·납입·분배)만 넣는다. 요청은 청구서라 `capital_call_items`에 둔다.
- **D9. 규약은 버전 행으로 관리**: 변경 이력 테이블 대신 조건 전체를 새 버전으로 추가한다. 어떤 시점이든 적용된 규약을 행 하나로 꺼낼 수 있다.
- **D10. 기업 정보는 `companies` 하나로**: 검토 기업과 투자 기업을 구분하지 않고, 포트폴리오는 뷰(`v_portfolio`)로 만든다.
- **D11. LP 공개 범위는 테이블 단위 등급**: 본인 것만 / 조합 단위 / 요약만 / 비공개 4등급. 기준이 단순해 실수로 데이터가 새기 어렵다.
- **D12. LP 연동은 아웃박스 방식**: 데이터 변경과 연동 이벤트 기록을 같은 트랜잭션으로 묶어, 저장과 알림이 어긋나지 않게 한다.

## D13~D19. 비즈니스 규칙 (2026-09-27 확정)

상세 규칙은 [04 비즈니스 규칙](04_business_rules.md)에 있다. ⚠️ 표시된 항목은 실무 확인 후 바뀔 수 있다.

- **D13. 1원 단위 나머지 처리**: 원 미만 버림 후, 나머지는 약정액이 가장 큰 조합원에게 붙인다 (동률이면 먼저 가입한 조합원). 최대 잔여 방식은 더 공평하지만 설명이 복잡하고, GP 부담 방식은 GP 약정이 작을 때 어색해서 채택하지 않았다.
- **D14. 투자 시 현금 잔액도 검사**: 약정 기준 투자 가능 잔액과 현금 잔액을 모두 검사한다. 캐피탈콜 → 투자 순서를 시스템이 강제해, 현금이 마이너스가 되는 기록을 막는다.
- **D15. 워터폴 단순화** ⚠️: 조합 전체 기준 누적 계산, 원금 반환 → 기준수익(단리) → 초과수익(조합원 / GP 성과보수). GP 캐치업과 클로백은 고도화 단계.
- **D16. 관리보수 단순화** ⚠️: 분기 청구, 일할 계산(365일). 투자 기간 중에는 약정 총액, 이후에는 투자 잔액 기준. 경계에 걸친 기간은 두 행으로 나눈다.
- **D17. 가결 기준** ⚠️: 출석이 아니라 전체 의결권 대비 찬성 비율로 판정한다. 기권·미투표는 찬성이 아니다.
- **D18. 드롭된 딜은 종료 상태**: 다시 검토하려면 새 딜을 만든다. 단계별 소요 기간 분석이 깨끗해진다.
- **D19. 최초 납입은 결성 전 허용** ⚠️: 명부 확정 후 결성총회 전에 최초 캐피탈콜을 발송할 수 있고, 발송을 결성 조건으로 둔다. 납입 완료까지 요구할지는 실무 확인.

## D20~D26. API 설계 (2026-09-27 확정)

상세 내용은 [05 API 설계](05_api_design.md)에 있다.

- **D20. 모든 API를 REST 방식으로**: Server Actions는 코드가 짧지만 API 목록이 문서로 드러나지 않고 LP 시스템이 쓸 수 없다. REST로 통일해 GP 화면·LP 시스템·테스트가 같은 창구를 쓴다.
- **D21. 필드 이름은 snake_case**: DB·용어 정의와 같은 이름을 써서 변환 실수를 없앤다.
- **D22. 돈이 움직이는 요청은 멱등성 키 필수**: 중복 클릭·자동 재시도로 같은 돈이 두 번 기록되는 것을 막는다. `idempotency_keys` 테이블 추가 (테이블 28개).
- **D23. 상태 변경은 동작 API로 분리**: `PATCH status` 대신 `/issue`, `/confirm`, `/transitions` 등. 조건 검사와 부수 작업을 빠뜨리지 않는다.
- **D24. LP 연동 인증은 시스템 간 API 키 + 경로의 `lp_id`**: LP 사용자 로그인은 LP 시스템이 책임지고, GP는 LP 공개 등급으로 데이터를 거른다.
- **D25. 웹훅은 서명 + 재시도 + 빠진 이벤트 조회 API**: 위조 방지, 일시 장애 대응, 누락 복구를 모두 갖춘다.
- **D26. 금액 계산은 미리보기 API를 따로 둔다**: 저장 전 확인이 가능하고, 미리보기와 저장이 같은 계산 함수를 쓴다.

## D27. 로그인 세션은 DB 세션 테이블 (2026-09-27 확정)

- **결정**: 로그인할 때마다 `sessions` 테이블에 한 행을 저장하고, 쿠키에는 무작위 토큰만 넣는다. DB에는 토큰의 SHA-256 지문만 저장한다.
- **검토한 선택지**
  - 서명된 쿠키: DB 테이블이 필요 없고 빠르지만, 특정 사용자를 강제 로그아웃하려면 만료까지 기다려야 한다
  - **DB 세션 테이블 (채택)**: 매 요청마다 DB를 한 번 더 조회하지만, 로그아웃·강제 로그아웃이 즉시 반영되고 접속 기록이 남는다
- **영향**: 테이블 29개. `sessions` 는 LP 공개 등급 🔴 비공개.

## D28. 데모 로그인 버튼 + 일반 로그인 (2026-09-27 확정)

- **결정**: 로그인 화면에 "데모 계정으로 둘러보기" 버튼을 크게 두고, 아래에 이메일·비밀번호 로그인도 둔다.
- **이유**: 면접관은 클릭 한 번으로 들어가고, 실제 로그인 기능도 갖췄다는 것을 보여줄 수 있다.
- **구현**: `POST /api/v1/auth/demo-login` 이 데모 계정(`demo@vc-erp.dev`)으로 세션을 만든다. 데모 계정은 `npm run db:seed` 로 생성한다.

## D29. 최소 결성 기준: 결성 주체 유형 + 개인투자조합 + 1좌 금액 (2026-09-27 확정)

- **배경**: 목표 결성액에 제한이 없어 1원짜리 조합이나 0이 하나 더 붙은 오타도 저장됐다. 실무에는 조합 유형과 결성 주체에 따른 최소 결성액 기준이 있다.
- **결정**
  - 조합마다 **결성 주체 유형**(`gp_type`)을 저장한다. 한 회사가 벤처투자회사·신기사 자격을 함께 가질 수 있어 회사 설정이 아니라 조합 단위로 둔다.
  - 조합 유형에 **개인투자조합**을 추가한다.
  - 규약 조건에 **1좌 금액**(`unit_amount`)을 추가한다. 약정액은 1좌 금액의 배수여야 한다.
  - 기준표는 코드 한 곳(`lib/rules/fund-minimums.ts`)에 둬서 법령이 바뀌면 그곳만 고친다.
- **검사 시점**
  - 조합 생성·수정: 목표 결성액 < 최소 결성액이면 저장 차단 (BR-FUND-09)
  - 결성: 실제 약정 총액 < 최소 결성액이면 결성 차단 (BR-FUND-02)
  - 1조 원 초과: 오타 경고만 (BR-FUND-10)
- **미확인**: 신기술사업투자조합 최소 기준, 개인투자조합 결성 주체 제한 → [98 실무 확인 목록](98_practice_check.md)

## D30. 한국어 표준어는 "조합", 코드·DB 이름은 `fund` 유지 (2026-09-28 확정)

- **결정**: 화면, 문서, 오류 문구, DB 설명(comment)의 한국어 표준어를 "펀드"에서 **"조합"**으로 바꾼다. 테이블·컬럼·API 주소의 영어 이름(`funds`, `fund_id`, `/api/v1/funds`)은 그대로 둔다.
- **검토한 선택지**
  - **한국어만 변경 (채택)**: 국내 VC 실무 용어(투자조합)와 맞추면서, 영어 이름은 업계에서 널리 쓰는 `fund` 를 유지해 개발자가 이해하기 쉽다. 작업량이 작다
  - 영어 이름까지 변경(`partnerships`): 한국어와 1:1로 맞지만 DB·코드·API·문서 전체를 고쳐야 하고 영어권 관례와 다르다
- **예외**: "펀드레이징"(출자자 모집 활동)은 업계 용어라 그대로 둔다.
- **적용**: `004_rename_fund_to_johap_comments.sql` 로 DB 설명을 갱신. 이미 실행된 001~003 SQL 파일 안의 주석은 실행 기록이라 고치지 않는다.

## D31. 구성원(staff)과 로그인 계정 연결 (2026-09-28 확정)

- **배경**: 조합을 결성하려면 운용 인력을 지정해야 하고, 운용 인력은 회사 구성원 중에서 고른다. 기존에는 로그인 계정(`users`)만 있고 인사 정보가 없었다.
- **결정**
  - 구성원을 별도 테이블(`staff`)로 만든다. 사번, 이름, 직위, 부서, 입사일·퇴사일, 연락처를 저장한다.
  - 로그인 계정과 **1:1로 연결**한다. 로그인하지 않는 구성원도 있을 수 있어 연결은 선택이다.
  - 영어 이름은 "조합원"(`fund_members`)과 헷갈리지 않도록 `staff` 로 한다.
  - 퇴사하면 행을 지우지 않고 퇴사일을 넣으며, 계정은 자동 중지된다. 담당 조합이 남아 있으면 퇴사 처리를 막는다.
  - 임시 비밀번호는 만들 때 한 번만 보여준다.
- **데모**: 구성원 5명과 로그인 계정을 `npm run db:seed-staff` 로 만든다. 계정 정보는 git에 올라가지 않는 `demo-accounts.md` 에 적는다. 기존 데모 버튼 계정은 박서연 수석심사역과 연결한다.

## D32. 조합 운용 인력: 역할 3종 + 교체 이력 + 결성 후 교체는 동의 필요 (2026-09-28 확정)

- **역할**: 대표펀드매니저(`lead`) / 핵심운용인력(`key`) / 운용인력(`general`). 대표펀드매니저는 조합당 1명.
- **이력**: 교체해도 이전 기록을 지우지 않고 선임일·해임일로 쌓는다. LP에게 중요한 정보라 LP 공개 등급 🔵(이름·직위·역할·기간).
- **결성 조건** ⚠️: 대표펀드매니저 지정을 결성 조건에 추가한다. 추가 요건은 실무 확인 목록 23번.
- **결성 후 교체**: 가결된 운용 인력 교체 안건(`manager_change`)이 있어야 한다. 실제 동의 절차는 실무 확인 목록 24번.
