# 99. 결정 기록

설계 중 내린 결정과 그 이유를 남긴다. 결정이 바뀌면 지우지 않고 새 번호로 추가한다.

---

## D1. MVP 범위: 조합 생애주기 6단계 전체 (2026-09-27 확정)

- **결정**: 기획 → 모집 → 결성 → 운용 → 보고·총회 → 회수·청산까지 모두 MVP에 포함한다.
- **조건**: 기능이 얇아지면 안 된다. 각 단계는 입력 → 처리 → 결과가 끝까지 이어져야 한다. 개발 기간이 늘어나는 것은 감수한다.
- **검토한 선택지**
  - 1~4단계 + 최소 보고: 빠르지만 조합 운영의 끝(분배·청산)을 경험할 수 없다
  - 결성까지만: 투자가 빠진 VC ERP가 된다
  - **6단계 전체 (채택)**: GP 업무 전체를 이해하고 있다는 것을 보여줄 수 있다
- **리스크와 대응**: 성과보수·관리보수·의결 기준은 실무 규칙이 틀리기 쉽다 → 단순화한 규칙으로 구현하고 문서에 ⚠️로 밝힌 뒤, 해당 릴리스 전에 실무 확인을 받는다.

## D2. LP 시스템 연동: DB 분리 + GP 원본 + API 연동 (2026-09-27 확정)

- **결정**: LP 시스템은 별도 앱·별도 DB로 만든다. GP DB가 원본이고, LP 시스템은 GP가 제공하는 연동 API와 이벤트 알림으로 GP 데이터를 받는다.
- **LP DB에 두는 것**: LP 계정, 통지 읽음 여부 등 LP 시스템에서만 생기는 데이터
- **검토한 선택지**
  - 같은 앱 안에 LP 화면: 가장 쉽지만 시스템 간 연동 경험을 보여줄 수 없다
  - DB 공유 + LP 전용 API: DB가 하나라 LP 시스템이 GP 구조에 묶인다
  - DB 완전 분리 + 전체 복제 동기화: 실제 대규모 서비스와 가깝지만 동기화 실패 처리가 과하게 어렵다
  - **DB 분리 + GP 원본 + API (채택)**: 복제를 최소화해 동기화 문제를 줄이면서, 시스템 간 연동 설계를 경험할 수 있다
- **비용**: Neon, Vercel 모두 무료 플랜 안에서 가능 (가입 시 한도 재확인)
- **GP 쪽에서 지금 준비할 것**: 모든 GP → LP 요청을 '통지'로 기록, 데이터별 LP 공개 여부 구분, LP 연동용 API

## D3. 금액은 원 단위 정수로 저장 (2026-09-27 확정)

- **결정**: 모든 금액은 `bigint`(정수), 원 단위로 저장한다. 비율은 `numeric`(정확한 소수)으로 저장한다.
- **이유**: 실수형(`float`)은 계산 과정에서 미세한 오차가 생긴다. 분배처럼 여러 조합원에게 나누는 계산에서 오차가 쌓이면 합계가 맞지 않는다.

## D4. 지분율은 약정액 기준 하나로 통일 (2026-09-27 확정)

- **결정**: 캐피탈콜 배분, 총회 의결권, 분배 비율 모두 `조합원 약정액 ÷ 약정 총액`을 쓴다.
- **검토한 선택지**: 분배를 납입액 기준으로 하는 방식도 실무에 있다. 미납 조합원이 있으면 두 기준의 결과가 달라진다.
- **이유**: MVP에서는 기준을 하나로 통일해 계산 흐름을 단순하게 유지한다. ⚠️ 실무 확인 후 필요하면 분배 기준을 규약 조건으로 추가한다.

## D5. 원장은 추가만 허용 (2026-09-27 확정)

- **결정**: 원장 행은 수정·삭제하지 않는다. 틀린 기록은 반대 금액의 취소 행을 추가한 뒤 올바른 행을 다시 추가한다.
- **이유**: 누가 언제 무엇을 바꿨는지 모두 남는다. 실제 회계 시스템과 같은 방식이고, LP 시스템에 변경 이력을 그대로 보여줄 수 있다.

## D6~D12. DB 설계 원칙 (2026-09-27 확정)

상세 근거는 [03 DB 설계](03_db_design.md) 각 테이블의 "설계 의도"에 있다.

- **D6. 기본 키는 UUID**: 두 시스템(GP·LP)이 ID를 그대로 공유할 수 있고, ID로 데이터 개수나 순서를 짐작할 수 없다. 사람이 읽기 어려운 단점은 화면에 회차 번호(`call_no` 등)를 따로 보여줘서 보완한다.
- **D7. 합계·잔액은 저장하지 않고 뷰로 계산**: 원본이 하나라 숫자가 어긋날 수 없다. 데이터가 매우 많아져 느려지면 그때 캐시를 추가한다.
- **D8. 캐피탈콜 요청은 원장에 넣지 않음**: 원장에는 확정된 돈(약정·납입·분배)만 넣는다. 요청은 청구서라 `capital_call_items`에 둔다.
- **D9. 규약은 버전 행으로 관리**: 변경 이력 테이블 대신 조건 전체를 새 버전으로 추가한다. 어떤 시점이든 적용된 규약을 행 하나로 꺼낼 수 있다.
- **D10. 기업 정보는 `companies` 하나로**: 검토 기업과 투자 기업을 구분하지 않고, 포트폴리오는 뷰(`v_portfolio`)로 만든다.
- **D11. LP 공개 범위는 테이블 단위 등급**: 본인 것만 / 조합 단위 / 요약만 / 비공개 4등급. 기준이 단순해 실수로 데이터가 새기 어렵다.
- **D12. LP 연동은 아웃박스 방식**: 데이터 변경과 연동 이벤트 기록을 같은 트랜잭션으로 묶어, 저장과 알림이 어긋나지 않게 한다.

## D13~D19. 비즈니스 규칙 (2026-09-27 확정)

상세 규칙은 [04 비즈니스 규칙](04_business_rules.md)에 있다. ⚠️ 표시된 항목은 실무 확인 후 바뀔 수 있다.

- **D13. 1원 단위 나머지 처리**: 원 미만 버림 후, 나머지는 약정액이 가장 큰 조합원에게 붙인다 (동률이면 먼저 가입한 조합원). 최대 잔여 방식은 더 공평하지만 설명이 복잡하고, GP 부담 방식은 GP 약정이 작을 때 어색해서 채택하지 않았다.
- **D14. 투자 시 현금 잔액도 검사**: 약정 기준 투자 가능 잔액과 현금 잔액을 모두 검사한다. 캐피탈콜 → 투자 순서를 시스템이 강제해, 현금이 마이너스가 되는 기록을 막는다.
- **D15. 워터폴 단순화** ⚠️: 조합 전체 기준 누적 계산, 원금 반환 → 기준수익(단리) → 초과수익(조합원 / GP 성과보수). GP 캐치업과 클로백은 고도화 단계.
- **D16. 관리보수 단순화** ⚠️: 분기 청구, 일할 계산(365일). 투자 기간 중에는 약정 총액, 이후에는 투자 잔액 기준. 경계에 걸친 기간은 두 행으로 나눈다.
- **D17. 가결 기준** ⚠️: 출석이 아니라 전체 의결권 대비 찬성 비율로 판정한다. 기권·미투표는 찬성이 아니다.
- **D18. 드롭된 딜은 종료 상태**: 다시 검토하려면 새 딜을 만든다. 단계별 소요 기간 분석이 깨끗해진다.
- **D19. 최초 납입은 결성 전 허용** ⚠️: 명부 확정 후 결성총회 전에 최초 캐피탈콜을 발송할 수 있고, 발송을 결성 조건으로 둔다. 납입 완료까지 요구할지는 실무 확인.

## D20~D26. API 설계 (2026-09-27 확정)

상세 내용은 [05 API 설계](05_api_design.md)에 있다.

- **D20. 모든 API를 REST 방식으로**: Server Actions는 코드가 짧지만 API 목록이 문서로 드러나지 않고 LP 시스템이 쓸 수 없다. REST로 통일해 GP 화면·LP 시스템·테스트가 같은 창구를 쓴다.
- **D21. 필드 이름은 snake_case**: DB·용어 정의와 같은 이름을 써서 변환 실수를 없앤다.
- **D22. 돈이 움직이는 요청은 멱등성 키 필수**: 중복 클릭·자동 재시도로 같은 돈이 두 번 기록되는 것을 막는다. `idempotency_keys` 테이블 추가 (테이블 28개).
- **D23. 상태 변경은 동작 API로 분리**: `PATCH status` 대신 `/issue`, `/confirm`, `/transitions` 등. 조건 검사와 부수 작업을 빠뜨리지 않는다.
- **D24. LP 연동 인증은 시스템 간 API 키 + 경로의 `lp_id`**: LP 사용자 로그인은 LP 시스템이 책임지고, GP는 LP 공개 등급으로 데이터를 거른다.
- **D25. 웹훅은 서명 + 재시도 + 빠진 이벤트 조회 API**: 위조 방지, 일시 장애 대응, 누락 복구를 모두 갖춘다.
- **D26. 금액 계산은 미리보기 API를 따로 둔다**: 저장 전 확인이 가능하고, 미리보기와 저장이 같은 계산 함수를 쓴다.

## D27. 로그인 세션은 DB 세션 테이블 (2026-09-27 확정)

- **결정**: 로그인할 때마다 `sessions` 테이블에 한 행을 저장하고, 쿠키에는 무작위 토큰만 넣는다. DB에는 토큰의 SHA-256 지문만 저장한다.
- **검토한 선택지**
  - 서명된 쿠키: DB 테이블이 필요 없고 빠르지만, 특정 사용자를 강제 로그아웃하려면 만료까지 기다려야 한다
  - **DB 세션 테이블 (채택)**: 매 요청마다 DB를 한 번 더 조회하지만, 로그아웃·강제 로그아웃이 즉시 반영되고 접속 기록이 남는다
- **영향**: 테이블 29개. `sessions` 는 LP 공개 등급 🔴 비공개.

## D28. 데모 로그인 버튼 + 일반 로그인 (2026-09-27 확정)

- **결정**: 로그인 화면에 "데모 계정으로 둘러보기" 버튼을 크게 두고, 아래에 이메일·비밀번호 로그인도 둔다.
- **이유**: 면접관은 클릭 한 번으로 들어가고, 실제 로그인 기능도 갖췄다는 것을 보여줄 수 있다.
- **구현**: `POST /api/v1/auth/demo-login` 이 데모 계정(`demo@vc-erp.dev`)으로 세션을 만든다. 데모 계정은 `npm run db:seed` 로 생성한다.

## D29. 최소 결성 기준: 결성 주체 유형 + 개인투자조합 + 1좌 금액 (2026-09-27 확정)

- **배경**: 목표 결성액에 제한이 없어 1원짜리 조합이나 0이 하나 더 붙은 오타도 저장됐다. 실무에는 조합 유형과 결성 주체에 따른 최소 결성액 기준이 있다.
- **결정**
  - 조합마다 **결성 주체 유형**(`gp_type`)을 저장한다. 한 회사가 벤처투자회사·신기사 자격을 함께 가질 수 있어 회사 설정이 아니라 조합 단위로 둔다.
  - 조합 유형에 **개인투자조합**을 추가한다.
  - 규약 조건에 **1좌 금액**(`unit_amount`)을 추가한다. 약정액은 1좌 금액의 배수여야 한다.
  - 기준표는 코드 한 곳(`lib/rules/fund-minimums.ts`)에 둬서 법령이 바뀌면 그곳만 고친다.
- **검사 시점**
  - 조합 생성·수정: 목표 결성액 < 최소 결성액이면 저장 차단 (BR-FUND-09)
  - 결성: 실제 약정 총액 < 최소 결성액이면 결성 차단 (BR-FUND-02)
  - 1조 원 초과: 오타 경고만 (BR-FUND-10)
- **미확인**: 신기술사업투자조합 최소 기준, 개인투자조합 결성 주체 제한 → [98 실무 확인 목록](98_practice_check.md)

## D30. 한국어 표준어는 "조합", 코드·DB 이름은 `fund` 유지 (2026-09-28 확정)

- **결정**: 화면, 문서, 오류 문구, DB 설명(comment)의 한국어 표준어를 "펀드"에서 **"조합"**으로 바꾼다. 테이블·컬럼·API 주소의 영어 이름(`funds`, `fund_id`, `/api/v1/funds`)은 그대로 둔다.
- **검토한 선택지**
  - **한국어만 변경 (채택)**: 국내 VC 실무 용어(투자조합)와 맞추면서, 영어 이름은 업계에서 널리 쓰는 `fund` 를 유지해 개발자가 이해하기 쉽다. 작업량이 작다
  - 영어 이름까지 변경(`partnerships`): 한국어와 1:1로 맞지만 DB·코드·API·문서 전체를 고쳐야 하고 영어권 관례와 다르다
- **예외**: "펀드레이징"(출자자 모집 활동)은 업계 용어라 그대로 둔다.
- **적용**: `004_rename_fund_to_johap_comments.sql` 로 DB 설명을 갱신. 이미 실행된 001~003 SQL 파일 안의 주석은 실행 기록이라 고치지 않는다.

## D31. 구성원(staff)과 로그인 계정 연결 (2026-09-28 확정)

- **배경**: 조합을 결성하려면 운용 인력을 지정해야 하고, 운용 인력은 회사 구성원 중에서 고른다. 기존에는 로그인 계정(`users`)만 있고 인사 정보가 없었다.
- **결정**
  - 구성원을 별도 테이블(`staff`)로 만든다. 사번, 이름, 직위, 부서, 입사일·퇴사일, 연락처를 저장한다.
  - 로그인 계정과 **1:1로 연결**한다. 로그인하지 않는 구성원도 있을 수 있어 연결은 선택이다.
  - 영어 이름은 "조합원"(`fund_members`)과 헷갈리지 않도록 `staff` 로 한다.
  - 퇴사하면 행을 지우지 않고 퇴사일을 넣으며, 계정은 자동 중지된다. 담당 조합이 남아 있으면 퇴사 처리를 막는다.
  - 임시 비밀번호는 만들 때 한 번만 보여준다.
- **데모**: 구성원 5명과 로그인 계정을 `npm run db:seed-staff` 로 만든다. 계정 정보는 git에 올라가지 않는 `demo-accounts.md` 에 적는다. 기존 데모 버튼 계정은 박서연 수석심사역과 연결한다.

## D32. 조합 운용 인력: 역할 3종 + 교체 이력 + 결성 후 교체는 동의 필요 (2026-09-28 확정)

- **역할**: 대표펀드매니저(`lead`) / 핵심운용인력(`key`) / 운용인력(`general`). 대표펀드매니저는 조합당 1명.
- **이력**: 교체해도 이전 기록을 지우지 않고 선임일·해임일로 쌓는다. LP에게 중요한 정보라 LP 공개 등급 🔵(이름·직위·역할·기간).
- **결성 조건** ⚠️: 대표펀드매니저 지정을 결성 조건에 추가한다. 추가 요건은 실무 확인 목록 23번.
- **결성 후 교체**: 가결된 운용 인력 교체 안건(`manager_change`)이 있어야 한다. 실제 동의 절차는 실무 확인 목록 24번.

## D33. 조합원 명부 확정 기록 테이블 (`fund_rosters`) (2026-09-28 확정)

- **배경**: 명부를 확정하면 약정 원장 행을 만드는데, 원장 행은 원인 문서(`source_id`)가 반드시 있어야 한다 (BR-LED-03). 또 결성총회 전에는 명부를 취소하고 다시 확정할 수 있어야 한다 (BR-MEM-05). 원장과 조합원 행은 지울 수 없어서, "지금 유효한 명부"를 따로 표시할 곳이 필요했다.
- **결정**
  - 명부 확정 기록을 `fund_rosters` 로 만들고, 약정 원장의 `source_id` 로 쓴다. 조합당 유효한 명부는 1개 (부분 유일 인덱스).
  - 취소하면 행에 취소 시각·사유를 넣고, 그 명부의 약정 원장을 취소 행(음수)으로 되돌린다. 행은 지우지 않는다.
  - 조합원(`fund_members`) 행은 원장이 참조하므로 지우지 않는다. 다시 확정하면 같은 행을 재사용한다. 현재 조합원 = 원장 약정 합계 > 0.
  - 명부가 확정된 동안 규약 버전 1은 바꿀 수 없다. 바꾸려면 명부를 취소한다.
- **다른 선택지**: 원인 문서 ID로 조합 ID를 쓰기 (테이블은 안 늘지만 취소·재확정 이력을 구분할 수 없음).

## D34. 조합 기타 비용과 재무 탭, 회계 처리는 별도 모듈로 (2026-09-28 확정)

- **배경**: 관리보수 외 조합 비용(회계감사·수탁·사무관리 보수, 설립 비용 등)을 기록할 곳이 없어 현금 잔액과 투자 가능 잔액이 실제보다 컸다. 조합의 돈이 어디서 들어오고 나갔는지 한곳에서 볼 화면도 없었다.
- **결정**
  - 기타 비용을 `fund_expenses` 테이블로 기록한다. 틀리면 지우지 않고 취소 표시를 남긴다.
  - 투자 가능 잔액과 현금 잔액에서 기타 비용을 뺀다 (실무 확인 12번의 가정을 변경).
  - 조합 탭에 **재무**를 추가한다: 요약 + 현금 흐름 장부(모든 입출금, 누적 잔액) + 기타 비용.
  - 조합 운영에 회계 처리(결산·재무제표·외부감사)는 필수다. 업무 기록에서 분개를 자동으로 만드는 **회계 모듈**을 별도 릴리스로 설계한다 (실무 확인 25~28번).
- **다른 선택지**: 비용을 관리보수 테이블에 함께 넣기 (산정 방식이 달라 구조가 맞지 않음), 비용을 조합원 원장에 기록하기 (조합원 돈이 아니라 조합 재산의 지출이라 맞지 않음).

## D35. 회계 모듈: 업무 기록에서 복식부기 자동 분개 (2026-09-28 확정)

- **배경**: 조합은 결산·재무제표 작성·외부감사를 해야 한다. 업무 기록만으로 만든 약식 재무제표로는 발생주의 조정(미지급비용 등)과 결산을 할 수 없다.
- **결정**
  - 계정과목표(`accounts`, 모든 조합 공통)와 분개장(`journal_entries` + `journal_lines`)을 둔다. 분개장은 추가만 가능하고 정정은 역분개다 (원장과 같은 원칙, D5).
  - 업무 기록(납입·투자·관리보수·비용·회수·분배)과 **같은 트랜잭션**에서 자동 분개를 만든다. 업무 기록 하나에 자동 분개 하나 (DB 유일 인덱스).
  - 차변 합 = 대변 합은 서버 검사 + DB 지연 제약 트리거로 이중으로 지킨다.
  - 장부: 분개장, 계정별 원장, 시산표, 재무상태표, 손익계산서. 재무제표 화면에서 현금 계정과 현금출납장(업무 기록 기준)을 대사한다.
  - 결산: 사업연도 수익·비용을 이익잉여금으로 대체하는 결산 분개 + 기간 잠금(`fiscal_closings`). 잠긴 기간에는 업무 기록도 넣을 수 없다.
  - 수동 분개는 발생주의 조정용으로만 쓴다. 자동 분개를 손으로 고치지 못하게 해 업무 기록과 장부가 어긋나지 않게 한다.
  - 도입 전 업무 기록은 같은 규칙으로 한 번 소급 분개한다 (`npm run db:backfill-journal`).
- **가정 ⚠️**: 사업연도 1/1~12/31(결성 첫해는 결성일부터, 실무 확인 25), 투자자산 원가법(공정가치 평가는 분개하지 않고 참고 표시, 27). 분배금은 R6에서 출자금 반환·이익 분배로 나눈다.
- **다른 선택지**: 분개를 저장하지 않고 업무 기록에서 매번 계산하기 (단순하지만 수동 분개·결산·감사 추적이 불가), 외부 회계 프로그램으로 내보내기만 하기 (GP 시스템 안에서 결산 숫자를 확인할 수 없음).


## D36. 메뉴·조합 탭 구조 정리: 업무 흐름별 2단계 탭 (2026-09-28 확정)

- **배경**: 조합 상세 탭이 14개로 늘어나 한 줄에 다 보이지 않고, 비슷한 업무(재무·관리보수·회계, 딜·기업)가 흩어져 있었다.
- **결정**
  - 조합 상세는 **큰 탭 5개 + 작은 탭**으로 나눈다. 큰 탭을 누르면 첫 작은 탭으로 간다.
    - 개요: 요약(진행 단계·다음 할 일·핵심 숫자·확인할 일) · 조합 정보(기본 정보·규약 핵심 조건·운용 인력·등록·관계 기관)
    - 출자자·조합원: 출자 제안 · 조합원·원장 · 캐피탈콜
    - 투자: 투자 집행 · 포트폴리오
    - 재무·회계: 현금·비용 · 관리보수 · 재무제표 · 장부(시산표·계정별 원장·분개장) · 결산
    - 총회·보고: 총회 · 규약 · 정기 보고
  - 결성 전에는 쓸 수 없는 탭도 숨기지 않고 "결성 후"로 흐리게 보여준다.
  - 사이드바의 딜 파이프라인과 기업을 **딜·기업** 한 메뉴로 합치고, 화면 위 탭으로 나눈다 (딜은 기업에 대한 투자 검토 건).
- **다른 선택지**: 탭 1단계 유지 + 가로 스크롤 (찾기 어려움), 조합 상세를 사이드바 하위 메뉴로 펼치기 (조합이 늘면 사이드바가 길어짐).

## D37. 회수·분배·해산·청산 구현 방식 (2026-09-28 확정)

- **배경**: R6에서 회수·분배·성과보수·해산·청산을 구현하면서, 설계 문서가 정하지 않은 세부(분배 진행 방식, 조합원별 배분 기준, 회계 처리)를 정해야 했다.
- **결정**
  - 회수: 기업별로 여러 번 나눠 기록한다. 전량 회수면 남은 원금 전액, 일부 회수면 원금을 직접 입력한다. 같은 트랜잭션에서 투자자산 처분 분개.
  - 분배: 초안(워터폴 계산 저장) → 확정(잠금 + LP 통지) → 지급(조합원 원장 + 분개). 진행 중인 분배는 조합당 1건. 확정할 때 다시 계산해 초안과 다르면 막는다.
  - 조합원별 배분: 원금 반환은 납입액, 기준수익은 조합원별 기준수익, 초과수익은 지분율, 성과보수는 GP. (D15의 "지분율대로"를 원금·기준수익에서는 실제 납입 기준으로 구체화 — 미납 조합원이 있어도 공정하게)
  - 회계: 분배금을 `출자금반환`(원금 반환분)과 `이익분배금`(나머지)으로 나눠 분배 1건 = 분개 1건. 성과보수도 이익 분배로 처리한다 ⚠️ (실무 확인 29).
  - 해산: 해산 안건 가결 → 해산일 = 해산총회일. 청산: 보유 기업 전부 회수 + 최종 분배 지급 + 현금 0 + 미마감 캐피탈콜 없음 → 청산일 = 최종 분배일.
  - 조합 탭: "투자" 묶음을 **투자·회수**로 바꿔 회수와 분배를 넣는다 (투자 집행 · 포트폴리오 · 회수 · 분배). 분배할 돈은 대부분 회수에서 나오므로 회수 → 분배를 한 흐름으로 본다. (처음에는 캐피탈콜의 반대 방향이라 출자자·조합원 묶음에 두었다가 2026-09-29 옮김)
  - 성과보수는 관리보수와 성격이 달라(정기 보수 vs 초과수익 분배) 따로 청구하지 않고 분배 워터폴에서만 계산하되, **재무·회계 > 성과보수** 화면에 조건·발생 기준선(납입액 + 기준수익)·지급 내역·공정가치 기준 예상액을 모아 보여준다.
- **다른 선택지**: 분배를 지급 기록 한 번으로 끝내기 (LP 통지·확정 절차가 없어 실무와 다름), 성과보수를 관리보수처럼 비용 처리 (GP 조합원 원장에 분배로 남기는 설계 D15와 어긋남 — 실무 확인 후 바꿀 수 있게 계정만 분리).

## D38. R7: 대시보드·통지·LP 연동 API·이벤트 전송 (2026-09-29 확정)

- **배경**: 성공 기준 6("모든 단계의 숫자가 대시보드와 일치하고, LP 한 곳 기준으로 공개 데이터만 조회된다")을 채우려면 대시보드와 LP 연동 API가 필요했다. 통지와 연동 이벤트는 R1부터 쌓이고 있었지만 볼 화면이 없었다.
- **결정**
  - **대시보드(홈 `/`)**: 조합 화면과 같은 원본(`v_fund_summary`, `v_portfolio`)으로 합계·조합별 숫자를 계산한다 (숫자가 따로 놀지 않게). 경고는 각 업무 규칙을 모은다: 의무투자, 캐피탈콜 미납·기한 초과, 만기 경과·임박, 지급 대기 분배, 작성 중 보고, 다음 단계 준비 완료, 연동 실패. 30일 안의 일정(납입 기한·총회·분배)도 보여준다.
  - **통지**: 조합 탭 **총회·보고 > 통지**. 자동 통지와 일반 공지를 한 목록으로, LP별 확인 현황과 함께. 일반 공지는 초안 → 발송.
  - **LP 연동 API** (`/api/lp/v1`): 시스템 간 API 키 하나(Bearer), 공개 등급으로 거른다. 같은 함수로 GP 화면에 **LP 공개 데이터 미리보기**를 만들어, LP가 무엇을 보는지 GP가 확인할 수 있게 했다.
  - **이벤트 전송**: 아웃박스 이벤트를 HMAC 서명 웹훅으로 보낸다. 주기 작업 대신 **LP 연동** 화면의 "지금 전송" 버튼과 API로 실행한다 (MVP. 운영에서는 Vercel Cron 등으로 같은 API를 주기 호출). 웹훅 주소가 없으면 대기로 두고 LP 시스템이 pull 할 수 있다.
- **다른 선택지**: 대시보드 숫자를 별도 집계 테이블로 저장 (원본과 어긋날 위험, D7에 어긋남), LP별 API 키 발급 (LP 사용자 인증은 LP 시스템 책임이라는 D2 원칙과 다름).

## D39. 정정: 회수 취소 · 분배 취소 · 결산 재개 (2026-09-29 확정)

- **배경**: R6까지 회수·분배는 추가만 가능했고 결산은 되돌릴 수 없었다. 잘못 입력하거나 결산 후 누락을 발견하면 고칠 길이 없었다.
- **결정**: 지우지 않고 **취소 표시 + 역분개**로 정정한다 (원장·분개장의 추가 전용 원칙 D5, D35와 같다).
  - **회수 취소** (BR-EXIT-08): 수정 대신 취소 후 재기록. 취소된 회수는 `v_portfolio`·현금·보고서에서 빠진다. 처분 분개 역분개일은 회수일(결산된 기간이면 오늘, 비용 취소와 같은 규칙). 회수일 이후 현금이 음수가 되면 막는다.
  - **분배 취소** (BR-DIST-12): 확정·지급한 분배를 `cancelled` 로. 누적 워터폴 때문에 **마지막 분배부터** 취소한다. 지급했던 분배는 조합원 원장 취소 행 + 분배 분개 역분개를 **오늘 날짜**로 남긴다 (실제로 돈이 돌아오는 날). LP에게 취소 통지.
  - **결산 재개** (BR-ACC-07): **마지막 결산부터** 연다. 결산 분개를 기말 날짜로 역분개하고 잠금을 푼 뒤 다시 결산한다. 결산 기록은 재개 표시로 남긴다 (연도당 유효한 결산 하나, 부분 유일 인덱스).
- **다른 선택지**: 회수·분배 수정 기능 (워터폴·원장·분개를 모두 다시 맞춰야 해 오류 위험이 큼), 결산 행 삭제 (이력이 사라짐), 분배 취소 행을 원래 분배일로 기록 (이미 나간 돈의 현금 흐름 이력과 어긋남).
- **한계** ⚠️: 지급한 분배를 조합원에게서 실제로 돌려받는 절차(반환 청구·확인)는 시스템 밖이다. 결산된 기간의 회수·비용을 취소하면 업무 기록은 원래 날짜에서 빠지지만 역분개는 오늘 날짜라, 과거 기준일의 현금 대사에 차이가 생길 수 있다 (결산 재개 후 취소하면 같은 날짜로 맞출 수 있다).

## D40. LP 직접 투표 (2026-09-29 확정)

- **배경**: MVP에서는 GP가 조합원별 찬반을 대신 입력했다. LP 시스템이 생기면 LP가 직접 투표해야 한다 (LP 서비스는 GP의 LP 연동 API로만 연동, D2).
- **결정**
  - LP 연동 API `PUT /lps/{lp_id}/funds/{fund_id}/meetings/{meeting_id}/votes`: 안건별 찬반을 한 번에 제출 (한 트랜잭션). 소집 후 개최 처리 전까지 재제출 가능.
  - `votes.channel` (`gp` / `lp_system`)로 누가 기록했는지 남긴다. LP 직접 투표는 GP가 바꿀 수 없고, LP 본인 제출은 GP 입력을 덮어쓴다 (본인 의사가 우선).
  - GP 입력은 서면 결의서처럼 시스템 밖에서 받은 의사를 옮겨 적는 용도로 계속 쓴다.
  - LP 조회 응답에 총회·안건 `id` 와 `voting_open`, `my_vote_channel` 을 더한다 (필드 추가라 기존 연동과 호환).
- **다른 선택지**: 안건 번호로 투표 (`agenda_no`) — 총회 id 는 어차피 필요하고, 안건 id 가 더 명확. 투표마다 웹훅 이벤트 — 제출한 쪽이 LP 시스템 자신이라 불필요 (결과는 기존 `meeting.result_finalized` 로 알린다).
- **한계** ⚠️: 투표 마감은 개최 처리 시점이다 (총회일 마감 등 별도 마감 시각 없음). 누가 투표했는지(LP 조직 안의 담당자)는 LP 시스템이 기록한다.

## D41. 이벤트 자동 전송(Vercel Cron) · 파일 첨부(Vercel Blob) (2026-09-29 확정)

- **배경**: 이벤트 전송은 "지금 전송" 버튼으로만 돌았고(D38), 규약 원문·보고서 PDF를 둘 곳이 없었다.
- **결정**
  - **자동 전송**: Vercel Cron → `GET /api/cron/dispatch-events` (`CRON_SECRET` Bearer 인증). **무료(Hobby) 요금제라 하루 1회** (00:00 UTC = 오전 9시 KST, `vercel.ts`). 유료로 바꾸면 5분 간격 등으로 줄인다.
  - **실행 잠금**: 자동·수동 전송이 겹쳐 같은 이벤트를 두 번 보내지 않게 `scheduled_jobs` 행 하나로 임대 잠금(5분)을 건다. 커넥션 풀러(pgbouncer) 때문에 세션 advisory lock 은 쓰지 않는다. 실행이 죽어도 임대 시간이 지나면 풀린다.
  - **파일 첨부**: 비공개 Vercel Blob 에 파일, `attachments` 에 메타데이터. 대상은 규약 버전·정기 보고. PDF만, 4MB까지 (서버 경유 업로드, 함수 요청 4.5MB 제한). 내려받기는 서버 경로로만 흘려보내 Blob 주소를 노출하지 않는다.
  - **LP 공개**: 오늘 적용 중인 규약 원문과 발행된 보고서 PDF만 LP 연동 API로 목록·내려받기 (🔵).
- **다른 선택지**: 파일을 Postgres(bytea)에 저장 — 외부 서비스는 없지만 DB 용량·백업 부담 (사용자가 Blob 선택). 브라우저 → Blob 직접 업로드 — 큰 파일 가능하지만 업로드 완료 콜백이 공개 주소를 필요로 해 로컬 개발이 복잡해 고도화로 미룸. 공개(public) Blob — 주소만 알면 누구나 받을 수 있어 조합 문서에 맞지 않음.
- **한계** ⚠️: 하루 1회 자동 전송이라 재시도 간격(1분~12시간)이 실제로는 하루 단위로 늘어난다. 파일 추가는 LP에게 별도 이벤트를 보내지 않는다 (보고서 발행 통지로 알게 된다).

## D42. 역할별 권한 · 감사 로그 (2026-09-29 확정)

- **배경**: 로그인한 GP 사용자는 모두 모든 작업을 할 수 있었고, 누가 무엇을 했는지 남지 않았다 (원장·분개의 `created_by` 정도).
- **결정**
  - **역할 4종**: 관리자 · 운용 · 재무 · 조회 (`users.role`). 돈이 실제로 움직이는 확인·지급·회계는 재무, 업무 문서의 작성·발송·확정은 운용으로 나눠 **직무 분리**를 한다. 관리자는 모두 + 구성원·권한·LP 연동·감사 로그.
  - **검사 한곳**: API 94개를 하나씩 고치지 않고, 모든 요청이 거치는 `withUser` 에서 주소 규칙표(`lib/auth/permissions.ts`)로 검사한다. 쓰기의 기본은 운용이고, 예외만 표에 적는다. 새 API를 만들어도 기본 규칙이 자동으로 걸린다.
  - **감사 로그**: 같은 곳에서 모든 쓰기 요청의 결과를 남긴다 (막힌 요청 포함). 로그인·로그아웃, LP 시스템 쓰기(통지 확인·투표), Cron 도 남긴다. 본문은 저장하지 않고 주소 모양 + 결과만 (비밀번호 같은 민감 정보가 로그에 들어가지 않게). 추가만 가능.
  - **데모**: 데모 버튼 계정은 관리자(모든 화면), 나머지 데모 구성원은 직위에 맞게 (대표 관리자, 관리팀장 재무, 심사역·파트너 운용).
- **다른 선택지**: 라우트마다 권한 검사 코드 삽입 (누락 위험), 조합별 권한(담당 조합만) — 운용 인력 지정(D32)과 연결하면 좋지만 지금 규모에서는 과함. 승인 절차(요청 → 승인) — 문서마다 상태가 하나 더 생겨 이번에는 하지 않음.
- **한계** ⚠️: 업무 화면의 버튼은 역할과 관계없이 보이고 서버가 막는다 (안내 메시지 표시). 감사 로그는 요청 단위라 "무엇이 어떻게 바뀌었는지"(변경 전후 값)는 각 업무 기록·원장·분개에서 본다.

## D43. 배포 환경의 데모 로그인은 조회 전용 (2026-09-29 확정)

- **배경**: 첫 배포를 앞두고 확인해 보니, 로그인 화면의 "데모 계정으로 둘러보기"는 누구나 누를 수 있고 데모 계정은 관리자다. 로컬과 배포가 같은 DB를 쓰므로, 공개 주소에서 누구나 실제 데이터를 바꿀 수 있게 된다.
- **결정**: 배포 환경(`VERCEL_ENV` 있음)에서 데모 버튼으로 만든 세션에 권한 상한(`sessions.role_cap = viewer`)을 둔다. 계정 역할은 그대로라 로컬 개발·시연에서는 관리자로 모든 기능을 쓸 수 있다. 조회 전용 세션은 화면 위 안내 띠와 사이드바 역할(조회)로 알 수 있고, 쓰기는 권한 검사(BR-AUTH-02)가 막는다.
- **다른 선택지**: 데모 계정 역할을 조회로 바꾸기 (같은 DB라 로컬 시연도 막힘), 배포 환경에서 데모 버튼 숨기기 (면접관이 둘러볼 수 없음, D28 목적과 어긋남), 배포용 DB 분리 (Neon 브랜치 — 데이터가 따로 놀아 이번에는 하지 않음).
